# ADR-0004：文档体系——按问题划分、单一真源、最终态

- 状态：已采纳
- 日期：2026-10-20
- 决策人：项目负责人
- 关联：[docs/README.md](../README.md)

## 背景

原有四份文档是需求、技术选型、架构、描述生成规范。二期设计定稿后，内容是以「一期 / 二期 / v1.1 补丁」的方式逐次追加的，带来几个问题：

- 同一信息多处出现：层次投影规则同时写在需求和架构里；数据格式同时写在技术选型和生成规范里；工程结构同时写在技术选型和架构里。
- 技术选型文档实际混着库选型、数据格式、工程结构、数据流、测试策略和分期计划，没有单一主题。
- 架构文档过长，同时承担总览和细节。

## 选项

| 选项 | 说明 | 结论 |
|---|---|---|
| A. 保持四份，继续增量修订 | 改动最小 | 否：冗余与不一致会随迭代累积 |
| B. 按问题重新划分，每类信息只有一个归属，架构拆成总览加专题 | 一次性重写 | 采纳 |

关于技术选型是否需要独立成文：库选型本质上是带理由的决策。它稳定、篇幅小，其结论（选择、理由、未选的方案）适合放进架构总览的「技术栈」一节。数据格式归描述格式文档；工程结构归架构的开发视图；分期计划不进仓库。独立成文的必要性因此消失。

## 结论

| 文档 | 回答 |
|---|---|
| 01 需求 | 做什么、为什么、做到什么程度（带编号与状态） |
| 02 领域模型 | 概念与领域规则（规则清单是单测的穷举依据） |
| 03 架构总览 + `architecture/` 5 个专题 | 怎么组成；每块怎么工作 |
| 04 描述格式 | 描述文件怎么写，设计版本怎么起草 |
| ADR | 为什么这样决定 |

文档描述最终态，用「状态」标注实现进度，不再保留按期次追加的章节。信息归属与维护约定见 [docs/README.md](../README.md)。

## 后果

1. `02-tech-selection.md` 删除，其内容分入 03（技术栈、开发视图）、04（格式与示例）；`04-model-generation.md` 改名为 `04-description-format.md`。
2. 需求编号保持原值；设计版本需求由 `V-n` 改为 `DV-n`，避免与规则 V 混淆；被合并的编号保留空号并注明去向。
3. 设计版本 phase2-dynamic 的规则清单是评审时的快照，定稿后以 02 为准。
4. 代码注释与本项目架构描述中的文档引用改指新位置。
