# ADR-0015：架构治理——代码事实、架构规则、棘轮门禁与 agent 接口

- 状态：已采纳（已实现）
- 日期：2026-10-21
- 决策人：项目负责人（方向与四处裁决，2026-10-21）；实现者提出的细化规则（来源「议」）列在 [02-domain.md](../02-domain.md) 的 K、U、Y、Q，待负责人确认
- 关联：需求 §2.1「支撑治理」、§4.8（GV）、§4.9（AG）、验收 §6.10；领域模型 §1.7、§2.14–§2.17；专题[架构治理](../architecture/governance.md)

## 背景

AI 时代代码大多由 agent 写，架构师要控制项目的迭代与演化，需要一个闭环：意图架构 → 对照代码事实发现偏离 → 把约束交给写代码的人与 agent → 记录演化。h5p-arch-desk 已经把「看懂系统」（分层、场景、设计版本）做到了，但：

1. 描述由 AI 生成，没有对照代码验证，445 条关系（h5player）是真是假无从判断；
2. 层的 `mayDependOn` 只展示不校验，设计版本定稿后不形成持续生效的约束；
3. agent 不在回路里：写代码前拿不到约束与语义，写完没人检查；
4. 没有度量结构腐化的指标，也没有「只许变好」的门禁。

对标德国 hello2morrow 的 Sonargraph（架构 DSL、默认拒绝、环度、基线棘轮，MCP 服务器 Zügel 在 agent 写代码前判定依赖、记录拦截），取其五点：

| # | 借鉴 | 本项目的做法 |
|---|---|---|
| 1 | 默认拒绝 + interface / connector | 模块的依赖白名单 `mayDependOn` 与访问面 `exposes`（缺省可写 `entry`，即 G10 的入口文件） |
| 2 | 环度（Σ 规模²）+ 基线棘轮 | 模块环度、文件环度；基线之外的新增违规、环度上升即门禁失败 |
| 3 | 写前判定 | `check_dependency`：判定之外附上目标模块的职责、访问面与接口签名——Sonargraph 没有的语义 |
| 4 | 拦截记录 | `governance/ledger.jsonl`：每次判定与重新扫描追加一行，可量化 |
| 5 | 事实层 | 接入层用 TypeScript 语法解析提取文件依赖（Zügel 不支持 TS），穿透 barrel 再导出 |

## 负责人裁决

| 问题 | 选项 | 裁决 |
|---|---|---|
| 规则写在哪 | A. 独立 `rules.yaml`，人定或经设计版本定稿，AI 重新生成当前版本时不得改动；层的 `mayDependOn` 仍在骨架 / B. 写在模块描述上 | **A**：规则是架构师的意图，不能被「迁就代码」的重新生成悄悄放宽 |
| agent 接口形态 | A. MCP + 命令行，共用一套查询核心 / B. 只做命令行 | **A** |
| 门禁口径 | A. 棘轮：基线内的违规只提醒，新增违规与环度上升为 error；无基线全部提醒 / B. 全部 error | **A**：存量可以逐步偿还，但不许变坏 |
| 页面范围 | A. 画布叠加 + 面板 / B. 只做命令行与 MCP | **A** |

## 结论

1. **事实层**（K）：接入层提取文件依赖（`import`、`import type`、`export … from`、`import()`、`require`，含 Vue 的 `<script>`），解析相对路径与工作区包名，命名导入沿再导出链追到声明文件；模型层按归属提升为模块依赖，与描述的关系比对：关系**已证实 / 未证实**，模块依赖**未描述**。只对当前版本、源码在本地时（开发态与命令行）。
2. **架构规则**（U）：`rules.yaml` 的 `rules` 定义模块白名单、访问面、例外、环的容忍；层的 `mayDependOn` 从「只展示」改为按默认拒绝校验（U2）。违规按（规则、规则所在模块、两端模块）计一条，带文件证据。
3. **环**（Y）：模块环与文件环为强连通分量，环度 = Σ 规模²；本层的环在画布上标出。
4. **棘轮门禁**（U8、U9）：基线 `governance/baseline.json` 由人用命令行生成并提交；`lint:model` 对当前版本报出：基线外的违规、环度上升为 error，基线内为 warning，无基线全部 warning。
5. **agent 接口**（Q）：命令行 `npm run arch -- <命令>` 与 MCP 服务器 `npm run arch:mcp` 共用查询核心：定位文件、描述模块、写前判定、违规、环、重新扫描、拦截报告；判定与重新扫描写拦截记录。agent 只读：不提供改规则、生成基线的工具。
6. **页面**（GV-5–GV-7）：顶部「代码事实」开关；画布上关系边标已证实 / 未证实，未描述依赖与违规画成不参与布局的叠加线，本层的环标在节点上；代码依赖叠加线可选中（`sel=d:`），面板列出证据；系统、模块、关系面板有「架构治理」一节；门禁 error 进问题提示。
7. `governance/` 目录不属于描述：读取描述、复制设计版本时都跳过；设计版本可以修改 `rules.yaml`（规则随设计评审演进），但设计版本不对应代码，不做事实比对。

## 后果

1. 模型层新增「架构治理」（`src/model/governance/`）；接入层新增「依赖提取」「治理存储」「agent 接口」；视图状态层的 DeskState 多一个事实同步；呈现层画布、面板、工具栏扩展。
2. 新增依赖 `@modelcontextprotocol/sdk`（及其所需的 `zod`），只用于 MCP 服务器，不打进页面。
3. 描述格式新增顶层键 `rules`；`mayDependOn` 的含义从「只展示」变为「校验」。首次扫描：本项目 0 违规、0 环；h5player 报出 287 条层违规（Application 经 `@h5player/framework` 直接依赖 Infrastructure 的 Framework），模块环度 604、文件环度 35877（最大的文件环 188 个文件）——基线由负责人评审后生成（U7）。
4. 运行视角下不显示代码事实叠加（舞台只回答「这一次怎么走」），面板照常。
5. 自举：事实层在本项目的描述里查出 13 条与代码不符的编译期关系与一个由文件归属不当造成的模块环，已按代码修正描述。
6. 后续：规则的版本对比（设计版本里 `rules` 的差异）、拆环建议的交互、按提交回看环度与违规的趋势。
