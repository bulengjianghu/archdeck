# ADR-0016：代码事实——概念子模块按宿主推出不判定，只引类型的依赖不算未描述

- 状态：已采纳（已实现）
- 日期：2026-10-21
- 决策人：项目负责人（决策 1 选「按宿主推出」，决策 2 选「细化两条规则」，2026-10-21）
- 关联：需求 GV-1、GV-2，验收标准 §6.10；领域模型 §2.14（K1a、K5、K5a、K7）；ADR-0015（代码事实层）

## 背景

按 ADR-0015 的代码事实比对本项目自己的描述（source.commit 8fae5e9）：未描述依赖 131 条，运行时关系未证实 21 条。逐条分类：

| 差距 | 类别 | 数量 | 例子 |
|---|---|---|---|
| 未描述依赖 | 有架构意义，应补关系 | 35 | 架构治理子模块之间（报告 → 事实 / 规则 / 环）；`state.transition.url` → 导航与场景路径 |
| | 类型或工具依赖 | 90 | 只引 `model.types` 的类型；`moduleName`、`*_LABELS` 这类名称查询与标签常量 |
| | 描述粒度 | 6 | 模型层入口 `index.ts` 的再导出；画布场景用了 Layout 入口文件里属于概念子模块的走线函数 |
| 未证实关系 | 经 HTTP、注入或回调，正常 | 10 | 项目视图经 HTTP 取描述；面板经注入请求副栏预览 |
| | 描述写错 | 2 | 对比基线其实由描述加载取得；归属投影已移到 `state.desk.files` |
| | 概念子模块，没有自己的文件 | 9 | `layout.ts` 一个文件对应四个子模块；DeskState 的 actions 在 `useDeskState.ts` 里；`project.ts` 内的四个子模块 |

两处是方向问题：

1. **概念子模块**：描述比文件粒度更细，子模块之间的关系在同一个文件里，导入永远证实不了。K5 原有的「依赖落在祖先上也算证实」只兜住了子模块与外部的关系，兜不住同一文件内的，也兜不住文件归兄弟模块的情况（`layout.ts` 归 runner，另外三个是它的兄弟）。另外，69 条已证实关系靠这条放宽，其中约 55 条是呈现层经 `useDesk()`（`inject.ts` 归 DeskState）访问 DeskState 的各个子模块：放宽同时承担着「统一入口」的情况。
2. **类型与工具依赖**：K1 按整条 import 语句判种类，`import { moduleName, type X } from '@/model'` 让穿透到 `types.ts` 的目标也记为 `value`；这类依赖占了未描述依赖的大半，逐条补关系会淹没真正缺的关系。

## 选项

决策 1（概念子模块）：

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 按描述拆文件 | 每个子模块一个文件 | 否决：为迁就工具改代码；`project.ts`（241 行）会拆成四个很小的文件 |
| B. 合并子模块 | 删掉子模块，职责并入拥有文件的模块 | 否决：下钻时失去文件内的结构；指向 actions 的关系会变成「连祖先」，违反 M6 |
| C. 描述里标 `kind: concept` | 加字段，K5、K7 跳过 | 否决：要人写能推出来的东西（原则 6），也容易被滥用来掩盖缺口 |
| **D. 按宿主推出** | 宿主 = 自身或最近的、有直接归属文件的祖先；两端宿主相同的关系不判定，标「概念拆分，同文件」；保留祖先放宽并改写理由 | **采纳** |

决策 2（类型与工具依赖）：

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 全部补关系 | 按第二级合并约 49 条 `depends` | 否决：图上噪声大，又是在手写能推出来的东西 |
| **B. 细化两条规则** | K1 按每个名字区分类型与值；K7 不计只引类型的依赖；剩下的值依赖（名称查询、标签常量）按代码补关系 | **采纳** |
| C. B 加「公共词汇」模块标记 | K7 跳过指向它的依赖 | 否决：要新字段并搬动代码，且可能变成什么都往里放的地方 |

## 结论

1. **K1a**：一个名字是类型，当它写成只引类型（`type X`、整条 `import type` / `export type`），或穿透后的声明是 `interface` / `type` 别名；一个目标只承接类型名时为 `type`。不按名称穿透的导入仍取整条语句的种类。
2. **K7**：只含 `type` 文件依赖的模块依赖不算未描述。类型是契约，由接口与数据结构描述；K5 的证实仍用类型依赖（`depends` 关系可由类型导入证实）。
3. **K5a**：宿主由归属推出，描述里不写标记。两端宿主相同的关系 `skipped` 并带 `host`，面板说明「不判定：概念拆分，同文件」。
4. **K5 的祖先放宽保留**，理由改写为「代码经祖先的文件进出」：统一入口（`useDesk()`），或概念子模块的代码在祖先的文件里。
5. 本项目描述随之修正：Layout 的三种排布挂到 `state.layout.runner` 之下（它们的代码在 `layout.ts`）；补 54 条关系（含模型层入口的 5 条再导出）；删掉 `rel.ad.versions-entry`，`rel.p7.projection-ownership` 改为 `rel.p7.files-ownership`（`state.desk.files` → 源码归属）。结果：未描述依赖 131 → 0，未证实 21 → 13（都是经 HTTP、注入或回调的运行时关系，不报警告）。

## 后果

1. 同一宿主内的关系不再给出证实信号：写错了也发现不了。这类关系只描述文件内的结构，导入本来就证实不了，靠评审把关。
2. 经回调连到概念子模块的关系（如 loading → actions、URL 同步 ↔ actions）宿主不同，仍为「未证实（运行时关系）」，不报警告。宿主互为祖先后代的情况（K4 去掉祖先后代之间的依赖，同样证实不了）是否也不判定，留待以后有实例时再定。
3. 声明为 `interface` / `type` 的名字即使没写 `type` 也按类型算：依赖导出解析（G11）给出的声明种类；追不到声明的名字按值算（保守）。
4. 验收 §6.10 第 5 条：本项目已无未描述依赖，叠加线在验收中靠去掉一条关系造出，浏览器端改用源码在本机的 h5player。
