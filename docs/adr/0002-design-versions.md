# ADR-0002：设计版本——每轮一份完整快照，与当前版本对比显示

- 状态：已采纳（被 [ADR-0023](./0023-sketch-reviewed-and-evolution.md) 修订：设计 = 架构师的草图 + AI 展开的轮次，草图对各轮与实现后的当前版本有约束力）
- 日期：2026-10-20
- 决策人：项目负责人
- 关联：需求文档 §4.1（DV-1–DV-7）、专题「描述加载与版本」、描述格式 §5

## 背景

迭代某个项目前（如本项目的二期动态视角），希望先由 AI 在当前架构上做扩展和调整，产出一份**设计版本**给架构师评审，多轮沟通后定稿再投入开发。设计版本不对应代码，但要和当前版本一样可以查看、选中、下钻。

需要决定：设计版本怎么存、多轮怎么留痕、评审时怎么看出「改了什么」。

## 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 增量（overlay）：只写新增 / 修改 / 删除的实体，加载时叠到当前版本上 | 文件小；当前版本更新后自动跟进 | 需要新的合并语义（删除、覆盖字段、移动父模块），Loader / Validator 都要改；当前版本重新生成后设计会悄悄变样 |
| B. 每轮一份完整快照：`designs/<设计>/r<N>/` 放一整套描述 | 模型层零改动，设计版本就是另一个「项目内容」；每轮都能单独打开、互相对比；当前版本重新生成不影响已出的设计 | 文件有重复；基线漂移需要提示 |

## 结论

采用 B。

```text
model/<项目>/
  system.yaml, modules/…           当前版本（由代码生成）
  designs/<设计 ID>/
    design.yaml                     设计元信息：名称、目标、基线、状态、各轮说明与评审意见
    r1/ system.yaml modules/…       第 1 轮完整快照
    r2/ …                           第 2 轮（根据评审意见修改后的完整快照）
```

- 读取当前版本时跳过 `designs/` 目录。
- 评审时界面把设计版本和**对比基线**（当前版本，或上一轮）做差异：新增 / 修改的模块、关系在图上标色，上级模块标出「内含 N 处变更」引导下钻，删除项在变更清单里列出。差异计算是模型层的纯函数 `diffModels`。
- 描述格式新增可选字段 `designNote`（模块 / 关系 / 接口 / 数据结构），写「为什么这样改」，只在设计版本里使用。
- 定稿后由开发按设计实现；实现完成、按代码重新生成当前版本后，设计版本保留作为记录（状态 `accepted` → `implemented`）。

## 后果

1. 模型层只多一个 `diffModels`，Loader / Validator / Indexer / Projector 不变。
2. 路由新增 `/p/<项目>/d/<设计>/<轮次>`；DeskState 多持有对比基线与差异结果。
3. `design.yaml` 记录基线 `base.commit`（取自当时当前版本的 `source.commit`）；当前版本重新生成后若与之不一致，界面提示「基线已漂移」。
   - 修订（ADR-0025，2026-10-24 协调者裁决）：草图 v2 的设计里 `base.commit` 改为**新建设计时仓库的 HEAD**（含描述目录），服务端在新建设计时写入；底稿与「相对基线」都从 `base.commit` 那一版描述读取；没有 git 或 HEAD 不含描述时省略，相对基线退化为相对当前版本。漂移改为比基线那一版与当前版本描述的 `source.commit`（旧设计仍按原口径）。
4. 每轮快照之间有重复内容，这是有意的：每轮都是可独立打开、可对比的完整架构。
