# ADR-0020：本地架构工作台——定位、存量封存与源码在本地的前提

- 状态：已采纳（已实现）
- 日期：2026-10-22
- 决策人：项目负责人（裁决 A、B、C，2026-10-22）
- 关联：01 §0、§2、§5；规则 G1、G2、K8、K9、U7、U8、Q7–Q10、E5、E6；需求 H-1、GV-6、GV-10、AG-4、DV-8；修订 [ADR-0007](./0007-source-files.md) 的前提；[ADR-0019](./0019-human-owned-writes.md)

## 背景

一次全面审查的结论（负责人认可）：产品骨架正确；问题在三处——定位叙事落后于实际（仍写「架构师只和图打交道」「构建成静态站点部署」）、几个闭环在工具外断开、信息层次让架构师把注意力花在噪音上（h5player 287 条存量违规淹没新问题，代码事实默认关闭）。工具擅长**发现**问题，但问题离开工具时是裸的：没有位置、没有根因、没有建议动作。

## 结论

| 裁决 | 内容 |
|---|---|
| A. 定位改为本地开发工具 | 叙事统一为「本地架构工作台：看见 · 对照 · 守住」：看见 = 结构 / 运行 / 设计版本 / 演化；对照 = 描述 vs 代码；守住 = 规则 / 环 / 门禁 / agent 写前判定。源码必在本地，开发服务器读源码、跑 TypeScript 解析、读 git、写本地文件；不考虑构建部署（ADR-0007 修订） |
| B. 存量封存进基线 | 生成并提交 `model/h5player/governance/baseline.json`；代码事实缺省开启，画布只叠加基线外的新增违规与未描述依赖，已知与已豁免的在面板分组列出（K9、GV-6） |
| C. media-web 移出 | 源码不在本地，不符合新前提；「源码不在本地」的提示与分支一并删除，读不到源码是配置错误（G1） |

审查中补上的闭环（实现者按负责人认可的审查结论提出）：

1. **返工清单**（Q7–Q9）：问题按根因聚合，每条带文件行号、规则编号与建议动作；命令行 `issues`、MCP `issues` 与页面问题页签（W-6）同一份结果，可「复制给 agent」。
2. **健康度为主**（Q10、H-1）：项目卡片先给描述问题、违规相对基线的变化、环、未证实、未归属，规模为次。
3. **看见演化**（E5、E6、DV-8）：读 git 历史，任意两个提交之间的描述差异按设计版本的方式标色。
4. **人拥有的文件可追加**（裁决 D，ADR-0019）。

## 后果

1. 构建态静态输出删除；`npm run build` 只做类型检查与打包验证。
2. 验收中「源码不在本机时跳过」的用例改为不设跳过：源码在本地是前提。
3. 新的门禁读数：h5player `lint:model` 为 0 个错误、287 条 `rule.known`，此后只许不增加。

## 修订：「议」规则的裁决（2026-10-22）

负责人逐条审阅 02 §2 中来源为「议」的规则（共 90 条，含 V4 的「Esc 返回上级」半条），裁决 4 条改写、其余批量确认。改写的规则来源记为「定（负责人 2026-10-22 裁决，ADR-0020）」。

| 规则 | 改为 | 理由 |
|---|---|---|
| Y1（Y3–Y5、Q2 的环影响随之） | 环（模块环与文件环）只按值依赖计算，只引类型的文件依赖（K1a 的 `type`）不作为环的边——与 K7「只引类型的依赖不算未描述」同口径 | TS 中类型环无害；计入让环度失真，门禁对真正的运行时环不敏感 |
| K4（G6、Q7 随之） | 归属冲突（G6）文件的文件依赖不提升到任何模块（两端任一为冲突文件的都不计），单独计数，并在返工清单的冲突项里注明「N 条依赖因冲突未计入」；冲突解决后自然计入。G6 的显示口径不变（文件仍同时列在各模块、投影时都高亮） | 冲突是描述问题，不该衍生出假违规与假未描述依赖 |
| K6（Q7、Q10 随之） | 运行时关系（calls / dataflow / event）未证实时，若两端之间（含祖先后代放宽，K5 口径）连类型依赖都没有，报 warning `fact.unconfirmed`、进返工清单；有类型依赖或经端口注入可解释的仍只在面板标注。实现细化：「两端之间有依赖」不论方向，祖先与后代之间的文件依赖（K4 不提升）也计入——祖先的文件组装子模块即注入 | 完全无依赖的运行时关系多半是描述写错 |
| V4、N9（N7、C-5、D-10 随之） | Esc 只取消选中，不再返回上级；返回上级只用 Backspace、面包屑、浏览器后退 | Esc 上钻容易误触 |

后果：

1. h5player 的环度：Y1 改写后模块 604 → 453、文件 35877 → 121；K4 改写后模块 453 → 38（文件环不经归属，不变）。违规：K4 改写后 287 → 178（109 条只由 14 组归属冲突文件的依赖衍生），返工清单的违规项 17 → 13。基线按改写后的口径重新生成并提交（只删键、无新增）；门禁口径（U8，违规与环度不许增加）不变。
2. h5player 的归属冲突文件（多为 `codeRefs` 的 glob 与单文件重叠，如框架公共类型契约的 `common/types/**`）承载的依赖暂不计入，相应的编译期关系变为未证实（`fact.unconfirmed` 提醒），收窄 codeRefs 后自然恢复。
3. K6 改写后，h5player 报警的未证实关系 26 → 134：新增 108 条两端无任何依赖的运行时关系（未证实的运行时关系共 115 条，只有 7 条有依赖可解释），其中 47 条的端点模块含归属冲突文件，收窄 codeRefs 后部分会恢复（K4）；h5p-arch-desk 自身按代码修正 2 条描述后仍有 7 条——跨进程的 HTTP / HMR 事件（页面 → ModelSource 插件，5 条）、经 vue-router 的导航（1 条）、经共用件注入键的 provide / inject（1 条），代码里本就没有两端之间的依赖，作为本条裁决的缺口留待负责人决定（不判定的口径，或保留提醒）。
