## 背景

架构师对一张架构图问的问题分两类：

| 问题类 | 典型问法 | 现在谁答 |
|---|---|---|
| 职责 | 这个模块做什么？谁负责后果？哪里可替换？ | 交互图（四类交互 + 机制、端口、边界角色，ADR-0029、ADR-0030）已答 |
| 变更 | 改一处会牵动哪里？耦合最重在哪？哪些模块最稳定、哪些最易变？分层有没有被穿透？ | 没有图答；只有散落的碎片 |

第二类问题全部是**依赖图**上的问题：改动沿导入关系传播（含只引类型——改一个类型，所有引用它的文件都要重编），耦合是依赖的条数与种类，稳定性是传入与传出依赖之比。依赖是代码事实，工具已经从源码精确算出（K1–K4、K12、K13、K5c），但它没有自己的投影，只以交互图的注解出现：

| 现象 | 根因 |
|---|---|
| **线型**：交互边的实线 / 虚线只说「这条交互有没有依赖撑着」（K5、K9），不说依赖本身；没有被交互覆盖的依赖（只引类型、纯值读取、由子类 / 组装 / 端口实现承载的）在图上一条都不出现 | 依赖只被当作交互的**证据**；ADR-0018 的信息层级把事实状态放在 T3「只标异常」，正常的依赖没有通道 |
| **面板「知识」行**：选中一条关系才看到「同向 / 反向 / 经端口 / 不判定」，一次一条 | 依赖按关系组织，没有按模块聚合、按层次投影的视图 |
| **叠加点线**（K9）：只画未解释的交互与基线外违规；两个项目现状 K7 为 0、没有新增违规，叠加线为零 | 叠加线按「异常」定义，正常依赖永远不画 |
| **环与违规**：本层环编号（Y4）、违规红晕；但「允许依赖谁」只在层的面板以文字出现，看不出一条依赖为什么合规 | 规则只在被违反时露面，没有「允许」的一面 |
| **端口面板、组装叠加、子类**：三种结构事实各有入口——端口在面板（K11）、组装在「显示」开关（O12）、子类在「知识」行旁（K12） | 三种结构事实没有统一的载体 |
| **指标缺失**：扇入扇出、稳定性没有算（[docs/system §5](../system/README.md#5-已知缺口按本文原则应补尚未做) 已登记缺口）；U11 疑似共用件内部算了入度却不显示 | 没有地方放：数字离开图就失去位置感 |

规模（第六轮头 094dcaa 实测；模块依赖按 K4，种类取该对模块文件依赖中最强的一种）：

| 项目 | 交互关系 | 模块依赖 | 其中交互使用 / 只有纯值读取 / 只引类型 | 文件依赖 | 组装 / 子类 | 入度最高的模块 |
|---|---|---|---|---|---|---|
| h5p-arch-desk | 423 | 555 | 416 / 51 / 88 | 1839 | 6 / 1 | `model.types` 122、`state.desk` 48 |
| h5player | 379 | 863 | 447 / 295 / 121 | 7684 | 145 / 23 | `infra.framework.contracts` 99、`domain.types.model-types` 76 |

约 1400 条模块依赖，在画布上常显的条数为零。交互图按「描述求准」（原则 SP6）刻意只收有架构含义的使用，正因如此它答不了变更类问题：被它略去的只引类型与纯值读取，正是改动传播的路径。

## 裁决

### A. 三视图分工

同一套模块层次（层次、视图节点、分级与折叠：L1–L4、O1–O11）上有三种边：

| | 结构图 | 交互图 | 运行图 |
|---|---|---|---|
| 边 | 模块依赖（K4），带档（交互使用 / 值使用 / 只引类型，K14）与结构记号（组装 K13、子类 K12、端口实现 K5c） | 关系：四类交互 `queries` / `commands` / `notifies` / `streams` + 修饰 `via` / `mode` / `pull`（§1.1） | 场景的有序消息（帧），每条绑定一条交互（S13） |
| 来源 | 代码事实，工具从源码算出（K1–K4），**不由人或 AI 写**（ADR-0026） | AI 的描述（主张）；核心之间由架构师写进草图确认（X23） | AI 的描述（场景）；证据文件（S15）与候选调用点（S16） |
| 时间轴 | 无：某一提交的编译期快照 | 无：「会这样交互」，没有先后 | 有：步骤顺序、分支、配对返回 |
| 回答 | 改哪、牵动哪里（影响面）、耦合最重在哪、哪些稳定 / 易变、分层违规与环 | 做什么、谁负责后果、哪里可替换（端口、边界） | 这一次怎么走、谁先谁后、查询有没有副作用 |
| 真伪 | 事实本身即真，不判真伪；只判**合规**（U2–U5、Y1） | 由依赖证实（K5、K5b、K5c）；无依赖的报 K6 | 由交互证实（S13 绑定、S19 形态）；无交互的为未建模（P11）；代码证据等级（S17） |
| 谁改变它 | 改代码（人或 agent），重新提取即变；规则 `mayDependOn` 由人定 | AI 重新生成描述；架构师改草图 | AI 重新生成场景；测试证据随代码 |
| 画在哪 | 结构视角（本 ADR 新增） | 交互视角（今「结构视角」） | 运行视角（不变，舞台为交互图，V5） |

**包含链：场景步 ⊂ 交互 ⊂ 依赖。** 绑定了关系的消息步骤是那条交互的一次发生（S13）；一条直接交互（不写 `via`）背后有一条依赖（K5）；经端口的交互背后是「发起方 → 端口定义模块」的依赖加接收方的实现者事实（K5b、K5c）。反向不成立：依赖多于交互（只引类型、纯值读取、组装、子类由事实承载，原则 SP6），交互多于场景步。经总线、经通道的交互越过导入图，不在包含链上，标「不判定」（K5b）——诚实地留缺口，不硬凑。

**互证：往上加语义，往下做证据。** 三个缺口各已有一条规则，本 ADR 只是让最底下的「依赖」也有自己的图：

| 方向 | 有上无下 | 有下无上 |
|---|---|---|
| 交互 ↔ 依赖 | 交互没有依赖撑着：未证实（K6） | 交互使用的依赖没有交互解释：未解释的交互（K7） |
| 场景步 ↔ 交互 | 消息没有绑定交互：结构中未建模（P11） | 交互从未在场景中出现：不报（场景只写有代表性的链路） |

这一节同步写进 [docs/system §3](../system/README.md#3-系统认知)。

### B. 命名

用词分三级，各有一义：**图**是一种边的集合（结构图 / 交互图 / 运行图）；**视角**是画布的模式，一种视角画一张图（结构视角 / 交互视角 / 运行视角）；**视图**是图在一个层次上的投影概念（02 §1.2、§1.11）。据此：

1. 02 §1.2 现名「结构视图」的交互图改名**交互视图**；该节的层次、视图节点、模块树、层次顺序、分层总览、分级是三种视角共用的，迁移时在节内注明「三视角共用」。
2. 新增的静态依赖图命名**结构视图**（02 §1.11），画它的模式叫**结构视角**。
3. 今天的「结构视角」（V1 中不开场景时的视角）改名**交互视角**；顶部切换由「结构 ｜ 运行：<场景名>」改为「结构 ｜ 交互 ｜ 运行：<场景名>」（V11）。
4. **运行视角不变**；它的舞台是交互图，「结构图作为舞台」一类说法改为「交互图作为舞台」。
5. 迁移清单见附录 A（96 条：文档 90 条、界面文案 6 条），连带术语见附录 B（49 条）；本 ADR 不改现有条目措辞，由实现会话按清单一次改完。代码标识符（`perspective: 'structure'`、注释）不在清单内，实现时一并决定（建议 `'interaction'` 承接现值，`'structure'` 给新视角）。

### C. 结构视图

1. **与运行视角并列，同一画布做模式切换**（V11）：不开场景时画布处于结构视角或交互视角，单击切换；打开场景即运行视角，退出回到进入前的模式；模式进 URL（`v=s`，交互为缺省不写）；缺省为交互视角，结构视角一次单击进入、URL 可直达（裁决 1）。不做三栏并列：ADR-0018 的根因正是「依赖作为背景与控制流平权」，三张图同时摆出是把同一个错误放大三倍（原则 SP4）；同一模块在三处出现，眼睛要来回对位。
2. **复用 L 规则的层次与布局，节点不动**（V12、L15）：视图节点、分级、折叠、边界角色的位置全部取交互视角的布局结果，三种模式之间不动；切换只换边与角标。依赖边不参与布局，按 L11 框外边的方式按需正交走线。位置不动是心智地图的锚：架构师在两张图之间对照的是「同一个位置上，两种边有什么差别」。
3. **边全部来自代码事实，不让人写**（K14、L16）：模块依赖（K4）按 `mapEndpoint` 投影到本层，一对节点一个方向按事实种类各成一条边——组装（K13）、子类（K12）、端口实现（K5c）各一条，其余的文件依赖为**依赖**——选中时都落到 K10 的同一个键（`sel=d:<依赖方>-><被依赖方>`）。依赖边的档取最强的一种：**交互使用**（`invokes`）> **值使用**（只有纯值读取）> **只引类型**，以浓淡区分；**只引类型的依赖边缺省收起，画布角计数，「显示」面板的开关打开**（裁决 2）。画法按裁决 D 的 UML 类图惯例（依赖虚线、继承实线 + 空心三角、端口实现虚线 + 空心三角、组装实线 + 实心菱形）；线宽是共享通道「聚合条数」。描述格式（04）不加任何字段（工程原则 6「能推出来的不让人写」）。
4. **选中模块显示影响面**（K15）：传入闭包（改它会牵动谁）与传出闭包（它要谁才能工作），按距离分档标在节点上，闭包外淡化；面板列计数与清单，可切换「影响面 / 依赖面」；计入只引类型（改类型会传播），面板与 `impact` 提供「只看值依赖」切换，环仍只按值（Y1 不变）（裁决 3）。
5. **块上标扇入 / 扇出与稳定性**（K16、L17）：扇入 Ca、扇出 Ce 按 M 子树外的不同模块计；不稳定度 I = Ce ÷（Ca + Ce），三档色条；按系统内不同模块数计、与层次无关，下钻不变，面板另列本层节点数（裁决 6）。
6. **`mayDependOn` 叠加为允许 / 违规**（U15）：每条依赖边按 U2–U5、U8 分违规（新增 / 已知 / 已豁免）、允许、无约束，**只标违规**（ADR-0018「只标异常」），允许的一面在悬停与面板说明是哪条规则允许。门禁不变（U8）。
7. **两张图互查**（K17）：每条依赖边带「被几条交互覆盖」（K7 的覆盖口径，另列端口 / 子类 / 组装事实的覆盖）；覆盖为 0、档为交互使用、又没有事实覆盖的，就是 K7，标「未解释」；覆盖为 0 而只是值使用或只引类型的是正常的知识依赖，不标（原则 SP6）。反向的 K6（有交互无依赖）画不成依赖边，在选中模块的面板「交互图互查」列出，可单击切到交互视角并选中。
8. **设计版本无源码时只画允许依赖图**（U16）：设计版本、提交版本没有代码事实（K8），结构视角只把层与模块白名单的 `mayDependOn`（该版本描述与活动草图）投影为允许边，注明「没有代码事实，只画允许依赖」；影响面、指标、覆盖、违规不适用。
9. **共用件折叠**（O13）——三种方案：

   | 方案 | 做法 | 结论 |
   |---|---|---|
   | 甲：照画 | 共用件的依赖边与其他边一样常显 | 否决：`model.types` 入度 122、`infra.framework.contracts` 99，每层都是以架为中心的星形，其余依赖被盖住（原则 SP4） |
   | 乙：隐藏 | 结构视角不画共用件的边、也不计入指标 | 否决：事实不可隐藏（原则 SP5）；共用件恰是改动牵动最广的地方，隐藏会让影响面系统性偏小 |
   | **丙：折叠但计数、按需展开、异常照画** | 共用件留在架上，与架之间的依赖边默认不画；使用者的「共用 ×N」角标在结构视角下计依赖（含只引类型）；悬停或选中时画出；反向依赖（U12）、违规（U15）、在环中（Y4）的照常画；指标（K16）与影响面（K15）对共用件照算、一条不少 | **采纳**：折叠不是隐藏——数字常驻、展开一步可达、异常不折叠；带宽留给非共用件之间的依赖，那才是架构上要看的耦合 |

   理由要点：SP5 约束的是「事实能否被看到与被计入」，不是「是否常显」；丙的每个共用件依赖都进了角标计数、指标与影响面，任何时候一次悬停可见。负责人裁决采纳丙，并在健康度加「入度最高的共用件」一条提醒（裁决 4，Q15）。

10. **运行视角不变**：舞台仍是交互图（V5）；步骤面板的「代码证据」一节在证据等级之上补一行包含链（步骤 → 交互 → 依赖，缺哪一级标哪一级），让三张图在一步上对齐（D-25）。

### D. 线型与图例按视图隔离（负责人 2026-10-24 提出，协调者细化）

1. **各自编码、各出图例**：三个视图各自定义边的视觉编码，各有一组图例；切换模式时图例整体替换，不混列（L19、D-26）。
2. **视图私有通道**——线型、色相、箭头与端点形状、浓淡，可在各视图重定义（L16、L18）：

   | 私有通道 | 交互视图（ADR-0018 不变） | 结构视图 | 运行视图（现状不变） |
   |---|---|---|---|
   | 线型 | 事实状态：实线 = 已证实或没有代码事实，虚线 = 未证实，点线 = 代码依赖叠加线 | UML 类图惯例：**依赖虚线**、**继承实线**、**端口实现虚线**、**组装实线** | 时序图按 D-6；舞台按 V5、V8 与回放临时线（P15） |
   | 箭头与端点 | 同步实心、异步空心「V」，经端口插座（L12） | 依赖开口箭头；继承、端口实现在被依赖方一端空心三角；组装在依赖方（组装者）一端实心菱形 | D-6 |
   | 色相 | 四类交互各一色（L10） | 中性，不表类型（种类由线型与端点表达）；`mayDependOn` 的允许 / 违规沿用治理色（U15） | 回放强调色（ADR-0018 T5） |
   | 浓淡 | 查询淡（L10） | 依赖的三档：交互使用深、值使用中、只引类型浅（缺省收起，裁决 2）；用明度，不用透明度（透明度属共享通道「变淡」） | — |

3. **三视图共享通道**——一个通道三处同义，不得各自重定义（L18）：节点形状与层次框（含分层总览的带、父模块框）；角色记号（核心、共用件架、`port` / `adapter`、总线）；选中（强调色窄晕）与聚焦变淡（透明度）；违规红晕；环的标记（本层环编号，Y4）；演化叠加（热度角标、耦合线，J5）；**线宽 = 聚合条数**（三档 1 / 2–4 / ≥5：交互视图是这条边合了几条关系，结构视图是合了几条模块依赖——都是「合了几条本图的边」，同义）。结构视图曾有「线宽表依赖档」的写法（草案 L16 的「线宽 = 文件依赖条数」与协调者给出的「线宽或浓淡」二选一），**显式否决**：线宽已是共享通道，档改用浓淡；文件依赖条数只进悬停与面板。
4. **理由**：ADR-0018 把虚线留给「未证实」，是因为交互图上每条线都是主张，真伪是最需要被看见的维度；结构图上没有主张、每条边都是事实，线型通道在那里无事可表，UML 惯例可以回来，让熟悉类图的读者零成本读懂。隔离的边界是「**私有通道可重定义，共享概念必须同义**」：节点、角色、选中、违规、环、条数在同一画布切换时若换了意思，同一个视觉信号在两种模式下说两件事，比不隔离更糟。
5. **ADR-0018 的适用范围**：ADR-0018 的编码限定为交互视图的编码（在其状态行加标注，不改原文）。

| 选项 | 否决理由 |
|---|---|
| 把静态依赖重新做成关系类型（`depends` 复活，或由事实自动生成写回描述） | ADR-0026 已否决：人或 AI 再写一遍是重复，完整性没有标准，驱动描述「求全」（原则 SP6）；自动写回则描述里混入机器算出的条目，来源不可区分（原则 SP2） |
| 在交互视图里叠加全部依赖线 | ADR-0018 的背景：依赖与控制流平权、一个通道表多个维度，曾让 153 条 `depends` 把调用系统性地画成灰色虚线；今天依赖（863）是交互（379）的两倍多，叠加后交互图的「只标异常」与查询淡 / 委托实的层级全部失效 |
| 只做指标表，不做图 | 表答得了「谁最稳定」，答不了「牵动哪里、经哪条路」与「违规落在哪两层之间」——心智模型是空间的（原则 SP1）；数字离开图就失去位置感。指标仍进面板（K16），但以图为主 |
| 三栏并列（结构 / 交互 / 运行同时显示） | 带宽（原则 SP4）：三张图同时摆出即 3 × 7 个主体；同一模块三个位置，对照靠眼睛来回找；画布三分后分层总览的带降到列数下限（O7）。模式切换加位置不动给出同样的对照，代价低一个量级 |
| 结构视角用自己的布局（按依赖方向分层，稳定的在下） | 位置随模式变化，对照失效；依赖方向的排布由不稳定度色条（L17）与 U17 的「逆稳定」记号部分承担（裁决 5：不要，位置不动） |
| 三视图共用一套边的编码 | 结构图的边全是事实，线型通道无事可表、白白浪费；且结构图的「依赖」（UML 惯例虚线）与交互图的「未证实」（ADR-0018 虚线）都想用虚线，同一画布上冲突（裁决 D） |
| 三视图完全独立，连共享概念也各自定义 | 节点、角色、选中、违规、环、条数在切换模式时换意思，同一个视觉信号在两种模式下说两件事，比不隔离更糟（裁决 D） |
| 指标做 Martin 全套（抽象度 A、主序列距离 D） | TS 的结构类型让「抽象」难以从语法判定（接口、类型别名、只有签名的对象都可能是契约）；先做不稳定度 I，A / D 仍留在 docs/system §5 |

## 已知风险

1. **两种箭头语义混读**：同一位置上交互图的箭头是控制流、结构图的箭头是依赖方向；多数直接调用两者同向，回调、通知、注入时相反，读者可能把依赖边当交互读。缓解：裁决 D——私有通道各自编码、图例整体替换（结构视图用 UML 惯例的线型与端点，与交互图的线型含义截然不同）、画布角常驻模式名。
2. **借来的位置不适合依赖**：节点位置由交互布局决定，依赖多而交互少的一对节点可能离得远，依赖边走线长、交叉多；根层与分层总览的依赖近乎全连接（任意两层之间都有只引类型的依赖），可能成毛线团。缓解：只引类型缺省收起（裁决 2）、按需走线、分层总览只画带间聚合边；仍不可读时以 h5player 实测结果再议（位置不动不变，裁决 5）。
3. **指标被误读为质量分**：I 高不等于坏（入口、组装根、呈现层天然 I ≈ 1），I 低不等于好（被大量依赖的契约只是难改）；Ca / Ce 以模块计，**随描述粒度变化**——AI 重新生成时拆合模块，数字就抖，心智模型跟着抖（原则 SP3 的反面）。缓解：只显示三档不排名次、面板写清解释、核心模块的数字随确认层（Z）一起看。
4. **影响面在环中失去信息量**：有环时传入闭包可能覆盖大半个系统（h5player 有模块环），「改它牵动一切」等于什么都没说。缓解：按距离分档、默认只展开距离 1、环成员标出（Y1）。
5. **共用件折叠让最大的影响面不在眼前**：改 `model.types` 牵动 122 个模块，但图上只有角标数字。缓解：选中共用件时照画其传入闭包（用户主动请求，带宽可接受）；健康度加「入度最高的共用件」提醒（裁决 4，Q15）。
6. **模式与交互视角的显示开关交叉**：「代码事实」（K9）、「组装」（O12）、关系类型筛选（L8）在结构视角下含义不同或无意义，开关是否随模式变化容易做乱。缓解：迁移时逐条标「只适用于交互视角」，结构视角的「显示」面板单列一组。
