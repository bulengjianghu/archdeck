# ADR-0029：四类交互与机制维度

- 状态：已采纳（待实现，第六轮）
- 日期：2026-10-24
- 决策人：项目负责人（2026-10-24 两次认可草案：`calls` 拆为查询 / 委托；实现契约降为端口上的事实；分类只确认核心模块之间的线）
- 关联：修订 [ADR-0026](./0026-relations-are-interactions.md)（关系四类：`calls` 拆为 `queries` / `commands`，`implements` 降为端口事实）、[ADR-0022](./0022-relation-semantics.md)（`implements` 与端口三角）、[ADR-0018](./0018-edge-encoding.md)（线型与箭头）；配套 [ADR-0030](./0030-boundaries-and-assembly.md)（边界与组装）；原则 SP1、SP2、SP3、SP4、SP5、SP6（[docs/system](../system/README.md)）；规则见「后果」；格式 [04 §3.3、§3.4](../04-description-format.md#34-关系)

## 背景

ADR-0026 把「谁知道谁」清出了关系，图上剩下的线都是交互；ADR-0027 把模块分了级。但架构师读一条线仍要靠猜：

| 现象 | 根因 |
|---|---|
| `calls` 占两个项目关系总数的八成以上（h5player 333 / 447，本项目 426 / 437），一条 `calls` 可能是「借个能力取个值」，也可能是「把一件事交出去、由对方负责后果」 | 两种性质完全不同的交互共用一个类型：前者后果归调用方、可随意缓存与重排；后者后果归被调方、是职责边界 |
| `implements` 与三类运行时关系并列，却是唯一按**知识方向**画箭头的线（实现方 → 契约所在模块） | 违反 ADR-0022「箭头 = 控制流」；「实现了哪个契约」是代码事实（类 `implements` / `extends`），不是交互的主张 |
| `via` 是一组平铺的字符串（`http` / `hmr` / `inject` / `router` / `callback` / `port` / `bus`），`port` 与 `bus` 不说经哪个端口、哪条总线 | 机制被当成了「证实不了的原因」，而不是交互的一个维度；端口与总线无法在图上被指认 |
| 端口三角（K11）的实现者来自 `implements` 关系、使用者来自 `calls` / `streams` 的 `to` | 端口不是实体，「B 能不能换掉」要靠拼三类关系推出来 |
| 继承（`extends` 基类）被迫写成 `calls`（第五轮 T4 保留了 15 条「继承基类经 `super` 调用」类的 `calls`） | 继承是结构事实，没有一类合适的关系可写 |

目标：**每条线只用三个判断题就能读出含义**（原则 SP1、SP4），能从代码算出的一律做事实（原则 SP5、SP6），分类是 AI 的主张、由架构师在核心之间确认（原则 SP3）。

## 裁决

### 1. 关系只表达交互，四类

| type | 名称 | 判据 | 同步性 | 后果归属 |
|---|---|---|---|---|
| `queries` | 查询 | 要结果、无副作用 | 同步缺省，可异步（`mode: async`） | 调用方 |
| `commands` | 委托 | 控制权交出，被调方拥有状态与副作用；可要回执 | 同步，或异步（`mode: async`） | 被调方 |
| `notifies` | 通知 | 委托的一对多：发布者不知道订阅者、不要结果 | 一律异步 | 订阅者 |
| `streams` | 流 | 同一通道上的连续数据项，关注吞吐与背压 | 推送（缺省）或拉取（`pull: true`） | 接收方 |

- `calls` 废除，按上表拆为 `queries` / `commands`；`implements` 作为关系类型废除，降为端口上的实现者事实（裁决 4）。
- 箭头一律是控制流方向（ADR-0022 不变）。
- **通知一律异步**（第五轮遗留「notifies 是否一律按异步呈现」的裁决）：场景里绑定到 `notifies` 的消息一律是 `async` 步骤（S19）；`mode` 写在 `notifies` 上为多余，提醒并去掉（M13）。

### 2. 机制维度 `via`

`via` 是四类交互都可挂的修饰，说明「经什么连」：

| `via` | 含义 | 证实（K5b） |
|---|---|---|
| 不写 | 直接：发起方导入接收方 | 按 K5 |
| `port:<接口 ID>` | 经端口：发起方只知道端口（接口），接收方是它的实现者 | 发起方 → 端口定义模块的依赖 + 接收方是该端口已证实的实现者，为已证实（经端口）；否则不判定 |
| `bus:<模块 ID>` | 经总线：两端只认识总线（`role: bus` 的模块，M14） | 不判定 |
| `channel:<通道名>` | 经通道：跨进程、框架注入、路由、组装者注入的回调等，静态导入证实不了 | 不判定 |

旧的平铺取值是迁移期别名（M20）：`http` / `hmr` / `router` / `inject` / `callback` 读作 `channel:<同名>`；`bus` 在系统里恰有一个 `role: bus` 模块时读作 `bus:<它>`；`port` 读作「端口未指明」并提醒。

### 3. 架构师的读法：三问四修饰

图例、`docs/system` 系统认知节与面板都按这一个读法组织：

1. **被调方拥有后果吗？** 否 → 查询。
2. **是：发起方知道接收方吗？** 知道 → 委托；不知道、一对多 → 通知。
3. **传的是连续数据吗？** 是 → 流。
4. **修饰**：经什么连（直接 / 端口 / 总线 / 通道）、异步、拉取。

「三问四修饰」= 三个判断题定类型，第四步读修饰；修饰不升为类型。

### 4. 端口是一等实体

- 端口 = 现有的接口（`interfaces[]`），归属定义它的模块（`owner`）；接口新增 `implementedBy[]`：实现者模块列表（04 §3.3）。
- **实现者来源**：代码事实优先——类 `implements` / `extends` 解析到该接口、引用了接口名、或结构性满足，沿用 K5 的三档（已证实 / 结构性实现 / 证据像使用）；描述里的 `implementedBy` 是 AI 的主张、待事实证实；草图可声明「模块实现端口」，是架构师的主张、待实现（X24）。代码事实发现而描述没写的实现者在端口面板标「仅代码事实」。
- **继承不是关系**：`extends` 基类（不是端口）记为基类的**子类事实**（K12），面板「知识」行旁显示；不写关系。
- **画法**：经端口的线在目标端画插座记号（L12）；端口画在定义模块的边上并标实现者数，点开列出实现者（L13）；K11 的端口三角改为**端口面板**（定义 · 实现者 · 使用者）。

### 5. 规则变化

- **M11** 改写：`via: port:<P>` 的 P 必须是已声明的接口，`via: bus:<M>` 的 M 必须是 `role: bus` 的模块；否则提醒并去掉坏的 `via`（同 M7 级）。原「`implements` 的目标须声明接口」随 `implements` 废除并入 M17。
- **M17**（迁移期映射）：读到 `calls` 记为「未分类」并提示 `relation.unclassified`；读到 `implements` 记为对应端口的 `implementedBy` 并提醒 `relation.implements-migrated`。
- **K5**：查询 / 委托的证据同原 `calls`；实现者证据三档移到端口（K5c）。**K6、K7** 按四类；K7 的覆盖加上端口实现者与子类事实。
- **新 U 规则**：查询的闭包里出现委托 / 通知 → 警告「查询有副作用」（U13）；端口无实现者、有实现者无使用者 → 提醒（U14）。
- **S 系列**：场景消息绑定——查询为 `call`（可配 `return`），委托按 `mode`（同步 `call`、异步 `async`），通知为 `async`，流不比（S19）。
- **分类是主张**：AI 用启发式建议分类（目标为共用件、有返回值、目标无状态持有 → 查询；返回 `Promise<void>`、目标持 store / 类实例、链路上有通知 → 委托）；lint 的「未分类」是提示不是错误；**架构师只确认核心模块之间的线**（负责人裁决），确认的方式是把类型写进草图（X1：草图写了的字段 AI 不得重定义）。

### 6. 迁移

- 两个项目约 760 条 `calls`（h5player 333、本项目 426，其中骨架 66 条在人拥有的 `intent/skeleton.yaml`）→ `queries` / `commands`：AI 分类 + 清单核对（30 条样本进报告）；人拥有文件的改动由负责人核对后 `arch own` 登记。
- h5player 30 条 `implements` → 对应端口的 `implementedBy`；为凑交互写的继承类 `calls` → 子类事实。
- 设计版本各轮同样迁移；违规基线不含关系类型，不变；K7 结果应仍为 0。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 把同步 / 异步、拉取 / 推送升为类型 | 修饰升类型让三问变五六问；同一交互换个调用方式就换类型，类型不稳定 |
| 保留 `implements` 与四类并列 | 机制与语义混在一个选择题里；且它是唯一按知识方向画箭头的线，违反 ADR-0022「箭头 = 控制流」 |
| 引入万能 `uses` | 对画图够、对推理不够——读不出后果归谁、能不能换；与去掉 `depends` 的理由相同 |
| 端口只做呈现（从关系拼出三角），不做实体 | 「B 能不能换掉」仍要靠拼；实现者无处挂代码事实的证据 |
| 架构师确认全部线的分类 | 七百多条逐条确认即一键盖章（原则 SP3 的反面）；核心之间的线才承载架构决策 |
