# ADR-0051：模型层四层划分——契约 / 描述 / 解释 / 交付

- 状态：已采纳，已实现（含第二级模块升级与四层声明为层；负责人 2026-10-29 授权）
- 日期：2026-10-29
- 决策人：项目负责人（2026-10-29 认可四层原则，要求先改代码、再改架构文档，看过分层与模块关系后定稿）
- 关联：[ADR-0038](./0038-tiers-by-dependency.md)（L28 按依赖分层，本 ADR 说明它是证据不是原则）、[ADR-0013](./0013-code-structure-and-e2e.md)（模型层分组）、[ADR-0026](./0026-relations-are-interactions.md)（只读常量不写关系）；`docs/03-architecture.md` §3.3；规则 L28、K22

## 背景

模型层 11 个模块彼此调用密集，L28 按值依赖算出的层是 7 层（3/1/1/1/2/2/1），其中 4 层各只有 1 个模块。层号是「到汇点的最长依赖链」，回答「离契约几跳」，回答不了架构师真正要问的三件事：

- 改一个模块会波及谁？
- 一个新模块应该挂在哪、允许依赖谁？
- 这条依赖该不该有？

评审中还发现两处让分层失真的地方：入口 `src/model/index.ts` 把各子模块 `export *` 出去，代码事实把它算成「加载流水线依赖治理 / 返工 / 演化 / 确认 / 对比 / 意图」，并与 `diff → intent → load` 组成 3 环，靠「没人依赖 → 提到顶层」的入口对齐规则钉在第 1 层；加载流水线又因校验场景语义而直接依赖场景入口。

## 裁决

1. **四层，按「知识属于描述还是被描述的系统」划分**（不按 import 跳数）：

   | 层 | 回答的问题 | 模块 |
   |---|---|---|
   | L1 契约 | 描述长什么样 | 类型与 Schema |
   | L2 描述 | 文本怎么变成可信、可比的描述 | 加载流水线、场景语义、意图、版本对比、确认 |
   | L3 解释 | 这个系统是什么样 | Projector 层次投影、场景投影、源码归属、架构治理、演化事实 |
   | L4 交付 | 怎么组装给人 | 返工清单、模型层入口（`src/model/index.ts`） |

2. **依赖只能向下**（L4 → L3 → L2 → L1）；同层模块可以任意互相调用（它们是对等能力，不是上下级）；向上只有两种合法：控制反转（回调 / 通知 / `via`），或登记为例外。分层因此只约束方向，不禁止「模块相互独立、互相调用能力」。

3. **门面是 L4 的交付面**：入口的 `export *` 是导出面，不是知识依赖——它把 L2/L3 的能力按层交给外部，本身不含知识。代码事实仍会把它算成依赖，读图时按本条解释；它同时是 `rules.yaml` 里模型层唯一的访问面（`exposes: [entry]`）。

4. **场景语义下沉到 L2，作为代码接缝**：`src/model/scenario/semantics/`（步骤树、消息绑定、回放计划）是 L2，`src/model/scenario/`（路径、帧的层次投影、参与查询、步骤大纲、时序模型）是 L3。加载流水线的 Validator / Indexer 只依赖语义半区，访问面在 `rules.yaml` 里声明 `src/model/scenario/semantics/index.ts` 为唯一入口；投影半区不反向依赖加载流水线。

5. **画布继续显示 L28 算出的层**（诊断用），四层写进架构文档与评审清单（原则用）。两套判据并存：算出的层回答「离契约几跳」，四层回答「该不该依赖」。不把第二级模块改成四层——那会动骨架与确认记录（人拥有），且与访问面规则冲突。

6. **第二级模块已升级**（负责人 2026-10-29 授权）：把「模型层入口」（`model.api`，原 `model.pipeline.entry`）与「场景语义」（`model.scenario-semantics`，原 `model.scenario.flatten`）升为第二级模块，骨架、确认记录、访问面与两条关系端点（agent → 入口、返工清单 → 场景语义）随之更新。
7. **四层已声明为层**（负责人 2026-10-29 决定「把四层声明成层，打开这个模块就是 4 层」）：模型层的子模块改为四个层模块——`model.deliver`（交付，order 1）、`model.explain`（解释，2）、`model.description`（描述，3）、`model.contract`（契约，4）；每层 `mayDependOn` 写成「只可依赖下面的层」，把方向规则从文档约定变成可校验的层规则；其余模块按归属挂到层下并标 `core`（带内常显）。模型层因此由普通层次变为分层总览：打开即 4 条带，L28 的计算层不再作用于本层（其余层次不变）。

## 实现要点

- 代码：新增 `src/model/scenario/semantics/`（`index.ts` 作语义入口，`steps.ts` / `bind.ts` / `plan.ts` 迁入）；`validate.ts`、`indexer.ts` 改从 `./scenario/semantics` 取；`scenario/index.ts` 仍把语义与投影合起来对外，公开 API 不变。
- 描述：`model.scenario.flatten`（回放计划）的 `codeRefs` 指向语义目录；`rules.yaml` 的 `model.scenario.exposes` 由 `[entry, src/model/scenario/steps.ts]` 改为 `[entry, src/model/scenario/semantics/index.ts]`，理由同步写明「语义半区是 L2、投影是 L3」。
- 文档：`docs/03-architecture.md` §3.3 增「四层与依赖方向」小节与例外清单；L28 的说明补一句「层号是耦合深度，不是职责等级」。

## 代价与未决

- 骨架、确认记录与访问面是人拥有的文件，本轮按负责人授权改完后已重新登记指纹（`npm run arch -- own --project h5p-arch-desk`）；后续 AI 再动它们仍会报 `owned.changed`。
- 模型层改为分层总览后，带内模块之间的边不在带内画（分层总览的语义：带是这一层的框，只画跨带的核心边）；要看带内模块之间的关系，下钻到带里或看图例旁的面板。
- 四层的 `mayDependOn` 已成为层规则（U2）：跨层向上依赖会被判违规，不再只是文档约定；L28 仍用于其余普通层次。
- 四层里的 L2 / L3 边界只在场景一处落到目录；其余模块的归属是文档约定，尚无机器检查。若要把方向变成门禁，需要新规则（类似 K22 只管交互边），列入候选。
