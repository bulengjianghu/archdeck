# ADR-0053：选中面板五问与三卡；描述新增 summary / purpose / invariants

- 状态：已采纳（负责人 2026-10-30 审核第十七轮需求 R1、R3，D1–D3、D7）；描述契约（R1）已实现（第十七轮 W1），属性栏三卡（R3）待实现（W3）
- 日期：2026-10-30
- 决策人：项目负责人
- 部分取代：[ADR-0050](./0050-panel-skeleton.md) 的五段骨架（② 作用、④ 边界、⑤ 证据与细节的组织方式由本文的三卡取代；① 头部徽标槽位表保留）
- 关联：[ADR-0042](./0042-principles-three-levels.md)（原则三级：`abstraction` 在此收窄）、[ADR-0029](./0029-interaction-kinds-and-via.md)（关系的类型与机制）、[ADR-0052](./0052-strata-are-classifications.md)（层）；规则 M24、M27–M31、V15 / V15a–c、L46

## 背景

第十七轮的目标是让架构师更快建立系统的心智模型（结构 + 行为 + 原理）。实测选中 media-web-player 的「播放器 Kit」：面板内容高 1647px、可视区 922px，要翻 1.8 屏，首屏读不到「它是干什么的」。

**数据层面的问题比界面更大**（按描述文件统计，第十七轮分析 `00-look-panels.md` §2）：

| 项目 | 有职责的模块 | 职责首句平均字数 | 首句超过 60 字 | 关系有说明 | 关系说明首句平均字数 |
|---|---|---|---|---|---|
| media-web-player | 68 / 87 | 116 | 60 | 174 / 174 | 55 |
| h5player | 98 / 120 | 109 | 88 | 379 / 379 | 66 |

「一句话职责」在描述里并不存在：`responsibility` 写的是内容清单，真正的一句话反而写在 `abstraction` 里，`abstraction` 同时兼着职责与切分原则两件事。关系说明全都有，但写的是**机制**（「经 binder 惰性创建 StateMachineController」），不是**目的**（为了什么）。界面怎么排都排不出没有的字，所以契约先改、界面后改。

## 裁决

### 一、描述契约（R1，已实现）

1. **模块新增 `summary`**：一句话职责，≤ 30 字，动词开头，写对外承诺、不写内部构成（M27）。新增字段而不是给 `responsibility` 加长度约束（D3）：`responsibility` 的全文（负责什么、不负责什么）仍是核对与确认的依据，删短它会丢信息；两个字段各管一件事，C1「一处一事」。
2. **`abstraction` 收窄**为「内部切分的原则」一句，不再兼任职责（M24 的口径不变，含义收窄）。
3. **模块新增 `invariants`**：≤ 3 条，每条一句，可带 `adr`（M28）。前四问描述「它现在是什么样」，不变式回答「它为什么一直是这个样子」；没有它，心智模型是一张静态快照，不能拿来推理（「这里能不能加一个并发入口」）（D1）。两种写法（字符串、`{ text, adr }`）由模型层 `invariantsOf` 归一。
4. **关系新增 `purpose`**：≤ 20 字，从调用方的视角写「为了什么」；`description` 照旧写机制（M29）。目的进理解卡、机制进核对卡与悬停提示，C2「图说位置，字说意图」。
5. **取值与回退在模型层**（M30）：`summaryOf` / `purposeOf` 在字段缺失时回退为长文首句截断并标「待提炼」——换一个前端（属性栏、命令行、AI 查询）同样需要，按 CLAUDE.md §2 第 3 条属于模型层；字数按显示宽度计（全角 1、半角 ½）。
6. **提示不作为门禁**（R1.5）：超长、核心模块缺 `summary`、不变式超 3 条都是 info（进返工清单，不计入提醒数）；`lint:model` 的摘要给出覆盖计数（M31）。理由：设计版本是冻结的快照，历史轮次不该因新契约多出提醒；字段齐全靠重新生成与摘要计数推动，不靠拦截。
7. **确认指纹（Z2）暂不纳入** `summary` / `invariants`：它们是 `responsibility` / `abstraction` 的提炼，纳入会让全部已确认模块一次性跌回需复核；是否纳入列为待裁（见末节 Q1）。

### 二、选中面板：五问与三卡（R3，待实现）

选中一个模块时，架构师在问且只问五个问题，它们组成属性栏的**理解**卡（默认展开，一屏读完，R3.8 首屏守）：

| 问 | 回答它的信息 | 来源字段 |
|---|---|---|
| ① 它是干什么的？ | 一句话职责（粗体） | `summary`（回退见 M30） |
| ② 它里面怎么分？ | 原则一句 + 各层或子模块，每个一句话（「分层」与「子模块」合并为一节） | `abstraction`、`strata`、子模块的 `summary` |
| ③ 别人怎么用它？ | 接口 / 端口名 + 一句话用途 | `provides`、接口的 `description` 首句 |
| ④ 它和谁协作，为什么？ | 每行「← / → 对端 · 类型 · 目的」，同一对端合成一行，展开才逐条；悬停高亮画布上那条线 | 关系的 `purpose`（回退见 M30） |
| ⑤ 它靠什么保证不乱？ | 不变式，带 ADR 链接 | `invariants` |

其余信息服务的是另外两个动词「对照」与「守住」，归**核对**卡：卡片头给结论（「⚠ N 项要看 · ✓ M 项正常」），固定六行（证实、治理、表面、拆分、演化、确认），异常行下平铺出问题的条目，长清单折叠带计数；有异常自动展开（D7）。第三张**相关资料**卡列本模块的图解与参与的场景。原 ⑤「证据与细节」的全部内容归入核对卡，不丢信息。关系、端口、层、场景、步骤等对象的面板套同样的三卡骨架（D2）。理解卡不写画布已经表达的位置信息（在哪一层、可依赖哪些层只留链接，C2）。

## 实现要点

- 契约（已实现）：schema 的模块 / 草图模块加 `summary`、`invariants`，关系加 `purpose`；类型 `InvariantDef`；`src/model/contract.ts`（契约「类型与 Schema」：`textWidth`、`firstSentence`、`truncateWidth`、`summaryOf`、`purposeOf`、`invariantsOf`，只看单个实体的字段，呈现层可直接用）；覆盖计数 `contractCoverage` / `contractNote` 在返工清单（`rework/coverage.ts`）；Validator 的 `checkContract`（M27–M29）；返工清单的规则映射；`lint:model` 摘要的「契约」一段（M31）；草图核验把 `summary` / `invariants` / `purpose` 当文字字段比（X17）。
- 描述（已实现）：三个项目的当前版本补齐字段；写法与生成规则在 04 §3.2、§3.4。
- 属性栏（待实现，W3）：理解卡只读 `summaryOf` / `purposeOf` / `invariantsOf` 的结果，回退值显示「待提炼」；三卡骨架、V15 / L46 的修订随 W3 登记。

## 待裁

| 编号 | 事项 | 处置 | 理由 |
|---|---|---|---|
| Q1 | 确认指纹（Z2）是否纳入 `summary` / `invariants` | 暂不纳入 | 纳入会让全部已确认模块一次性需复核；它们是提炼，原文仍在指纹里 |
| Q2 | 提示的严重度用 info（不计入提醒数、不进 `lint:model` 明细） | info + 摘要计数（M31） | 历史设计版本是冻结快照；同 M23 / M24 的口径 |
| Q3 | 字数口径：全角计 1、半角计 ½ | 按显示宽度 | 属性栏宽度固定（330px），半角词按字符数计会把含英文标识符的句子误判超长 |
| Q4 | 「核心模块缺 summary」只对 `role: core` 提示，不对第二级模块提示 | 只对核心 | R1.5 原文；第二级模块由重新生成补齐，摘要计数可见 |
