# ADR-0030：边界与组装

- 状态：已采纳（待实现，第六轮）
- 日期：2026-10-24
- 决策人：项目负责人（2026-10-24 认可草案，本轮做）
- 关联：配套 [ADR-0029](./0029-interaction-kinds-and-via.md)（端口实体、继承为事实）；扩展 [ADR-0027](./0027-module-roles.md)（`role` 的取值）；原则 SP1、SP4、SP5（[docs/system](../system/README.md)）；规则见「后果」；格式 [04 §3.2、§3.6](../04-description-format.md#32-模块)

## 背景

架构师最常问的三个问题，现在的图都答不上来：

| 问题 | 现状 | 根因 |
|---|---|---|
| 系统的边界在哪？谁对外、谁接外部技术？ | 对外 API 模块（h5player 的 `infra.player-index`）、外部技术的适配器（各 plugin 适配器、三方库封装）与普通模块画法相同 | 角色只有核心 / 普通 / 共用件 / 总线（ADR-0027），没有「边界」这一面 |
| 谁把这些部件装起来？换一个实现要改哪里？ | 组装根（h5player 的 `infra.bootstrap`）对各部件的 `new`、工厂调用、注册被写成 `calls`，与真正的运行时调用混在一起；或因只有 `new` 而成为「未解释的交互」 | 组装是结构事实（谁构造谁、谁注册谁），能从代码算出，却没有载体 |
| 先看哪条路径？ | 运行视角的场景列表把主流程、异常处理、维护类流程（重置、清理、热更新）平铺 | 场景没有分类 |

ADR-0029 把端口做成了实体（可替换点）；本 ADR 补上它的另外两半：**端口在系统边界上的位置**与**谁做组装**。三项都不增加关系类型（原则 SP4）。

## 裁决

1. **角色加两个值**：
   - `role: port`：系统对外的端口模块（对外 API、SDK 门面），画在系统框边上（L14）。
   - `role: adapter`：把外部技术接进来的模块（三方库封装、浏览器 API、外部媒体插件），贴外部系统一侧画（L14）。
   - 与 ADR-0029 的端口实体配合：端口（接口）说「契约在哪」，`port` / `adapter` 角色说「边界在哪」，可替换点因此可见。`role` 仍是单值；`port` / `adapter` 常显、不折叠进「+N」（O8），不进确认范围的扩展（Z4 不变）。写法与来源同其他角色（草图、`intent/roles.yaml`，M16）。
2. **组装事实**：从代码算出「A 组装 B」——A 的文件 `new` B 的类、调用 B 的工厂函数、把 B 的类或函数注册进容器（K13）。组装**不是关系类型**：面板「知识」行旁显示，分层总览与普通层次可打开「组装根」开关（O12），把组装事实投影到本层画成叠加线。组装根 = 组装了别的模块、自身不被任何模块组装的模块。只有组装而没有其他交互使用的依赖不再算「未解释的交互」（K7）。
3. **场景分类**：场景加 `kind: main | exception | maintenance`（缺省 `main`）；运行视角的场景列表默认只列主流程，可切到全部（R17）。
4. 依据：每项都改变架构师的一个决策（原则 SP1）——谁可替换（`port` / `adapter`）、换实现改哪里（组装根）、先看哪条路径（`kind`）；都不增加关系类型（原则 SP4）；组装从代码算、不让人写（原则 SP5、CLAUDE.md 工程原则 6）。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 组装作为第五类关系（`assembles` / `creates`） | 组装是能算出来的结构事实，写成关系即要求 AI 求全、人去确认，与去掉 `depends` 的理由相同（ADR-0026） |
| 用 `kind`（模块类别）表达端口与适配器 | `kind` 是「它是什么」（层、包、子系统、组件），角色是「它在本层承担什么」；边界属于后者，且要进草图对外的一面（X10） |
| `role` 改为多值（核心 + 端口） | 每个模块的呈现只能有一种（大块 / 架上 / 边上）；多值让呈现规则互相打架 |
| 场景按层次或发起者自动分类 | 主流程与异常的区别是意图，不是结构；能推出的（场景所在层次、触发者）已经推出 |
