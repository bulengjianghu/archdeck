# ADR-0033：把手——三个高度各答一个问题

- 状态：已采纳，已实现（第九轮 T2、T3）
- 日期：2026-10-27
- 决策人：项目负责人（2026-10-27 第九轮裁决：「三个高度各一条规则——总览只加把手数角标与悬停分组、不展开；普通层次展开散开时元素按所属子模块分组；内部层次现状」）；起草：第九轮执行会话
- 关联：承接 [ADR-0032](./0032-module-surface-and-carrier-chain.md)（表面元素 C1–C4、展开 C6、交互束按表面散开 D7）、[ADR-0027](./0027-module-roles.md)（核心模块与分层总览的跨层边）、[ADR-0021](./0021-orthogonal-routing.md)（走线；第九轮另一会话在其中补 O3a / O3b：总览核心边的端口与车道）、[ADR-0018](./0018-edge-encoding.md)（交互束按种类、线宽计条数）；规则 K18、L5、L10、L20、L20a、L23、L23a、O3、O4（02）；新增 L20b、L23b，修订 O4、L20a、L23a

## 背景

media-web-player 描述的分层总览里出现「自建时钟族 → 延迟决策律 ×5」：五条委托打到延迟决策律内部的三个子模块（运行骨架、计量、计时器），读者从一条束上看不出「打到内部哪几处」。模块划分评审（`plans/arch-desk-media-player/10-module-review.md`）说明根因是划分——五条里只有一条真的打到「律」——重划之后这条束会变成三条；但划分对了以后「一条束落在接收方的哪几处」仍是通用的问题：好的接口本来就该让多条交互经同一个模块的几个有名字的入口进来。

ADR-0032 已经给出「束按接口散开到表面元素」（D7），但只在普通层次、展开接收方时可见；分层总览不展开（节点不动、车道常留，O3b），读者在总览上什么都拿不到。

## 裁决

### 定义

**把手** = 一条交互束内各关系的 `interface` 对应的不同表面元素（K18 的声明接口：owner 在接收方子树内，或接收方 `provides`）。没写接口的、接口不在接收方表面上的落在模块本体，不算把手。每个把手属于接收方之下的某一个子模块——接口 owner 在接收方之下的那一级；owner 即接收方的属于「本体」。

把手只读描述（关系的 `interface`、接口的 `owner`），不要代码事实；分层总览与普通层次同一口径，设计版本同样有。

### 三个高度各答一个问题

| 高度 | 回答 | 画法 | 规则 |
|---|---|---|---|
| 分层总览 | 谁与谁、多重、**几个把手** | 核心跨层交互边角标 `×N · M 把手`，悬停按所属子模块分组列各条；不拆线、不展开 | O4、L23b |
| 普通层次（下钻到层） | 落在**哪几个把手**、把手属于哪块 | 收起态同样带角标与悬停分组；展开接收方时束散开到元素（L23），元素端口按所属子模块分组排列、组间细分隔、组首标子模块短名 | L20b、L23、L23b |
| 子模块内部层次 | 哪块接住了 | 现状：外部调用者作边界节点 | L4 |

### 为什么不在同一层画平行线

- 同一对节点之间的平行线只能表达「多」，表达不了「落在哪」：线的终点都是同一个节点框，读者还是要逐条悬停。
- 平行线把总览的车道与端口数量乘上去（O3b 刚定的「节点不动、车道常留」会被每条束的条数撑开），总览的任务是「谁与谁」，不是「每一条」。
- 「落在哪」的答案在接收方内部；要回答它就得把接收方打开（展开表面）。打开是下钻的事，所以放在普通层次；总览只给一个数（把手数）和一张清单（悬停分组），告诉读者值不值得下钻。
- 散开时元素按子模块分组，是把「落在哪个把手」再提升一级成「落在哪一块」：五个把手分在三块里，比五个并排的端口更接近读者要的答案；再往下（哪个类接住）是子模块内部层次的事。

### 角标与悬停的口径

- `×N · M 把手`：N 为束内关系条数，M 为把手数；M 为 0 或 N 为 1 时不写把手段（N 为 1 时同 L10 不标条数）。结构视角的束角标「×N 元素」（L21①）不变——那里的「元素」是依赖接到的表面元素，与交互的把手是两个维度。
- 悬停：「接口名 · 所属子模块 · 关系种类」，按所属子模块分组、组按条数降序（同数时子模块按声明顺序、本体在后）。
- 分层总览只给核心跨层边（O4）；带间的层间聚合边（O3）不带，那是层与层的整体关系，把手数没有意义。

### 与 ADR-0021 O3b 的关系

O3b 定的是「核心跨层边的端口在半边内按对端的横向位置排」：那是**几何意义**的次序——让线少交叉。本 ADR 的分组是**目标意义**的次序——让元素端口按「属于哪一块」排。二者作用在不同的端口上（总览核心边的端口 / 普通层次展开节点的元素端口），不冲突；总览不展开表面，所以总览上不会同时出现两种次序。

## 后果

- 02：新概念「把手」（§1.11）；新规则 L23b（角标与悬停分组）、L20b（展开元素按子模块分组）；O4 补「核心跨层边带把手角标、总览不展开」；L20a ⑦、L23a ⑤ 记实现细化。
- 01：需求补条目（见「把手」）。
- 实现：模型层 `bundleHandles`、`interfaceOwner`、`subUnder`、`elementOwner`、`elementSub`（`governance/carrier.ts`）；Layout `handleBadge`、`handleLabel`（`routes.ts`）、`coreHandleBadges`（`layered.ts`，只加独立函数，不动走线与端口）、`surfaceExpansion` 的 `groupOf`；DeskState `surfaceInfo.sub`、`surfaceSubOf`；画布 `SurfaceMarks` 的组间分隔与组首标签；面板「表面」一节分组。

## 实施结果（第九轮）

- media-web-player（重划前的描述）分层总览：自建时钟族 → 延迟决策律 `×5 · 5 把手`，悬停三组（计时器 3、运行骨架 1、计量 1）。方案预期写的是「×5 · 3 把手」，与「接口去重」的定义不符（五条的接口两两不同），按定义实现为 5，三是组数；记入负责人清单。
- pipeline 层：管线族 Provider → 延迟决策律为框外边，`×11 · 7 把手`；框外边按 L23 不散开，所以选中它时接收方虽然展开（节点加宽、端口按组排好），交互视角不画元素记号；结构视角选中延迟决策律可见四组（law / run / meters / timers）。
