# 产品定位与原则

> 本目录是架构台的最高层真源：它回答「这个产品是什么、为谁、按什么原则取舍」。01–04 与 ADR 的每一条结论都应能追溯到这里的一条原则；与本文冲突的规则以本文为准，改规则不改本文，改本文须记 ADR。决策记录：[ADR-0028](../adr/0028-positioning-and-principles.md)。状态：已采纳（2026-10-24）。
>
> 引用方式：其他文档只引用原则编号，写作「原则 SP<n>」，以免与 [02](../02-domain.md) 的场景规则 S1–S18 混淆；不复述原则内容。

## 1. 定位

架构台是架构师的**外脑，不是替身**。它把代码事实、AI 的描述、人的理解、人的意图分开存放，用不超过认知带宽的视图让架构师在每一个层次上都能看懂、确认、起草和验收。AI 的一切产出都是待确认的主张，人的一切产出都是待实现的意图，代码事实是裁判。系统持续演化，工具的任务是让每一次演化都经过人的理解。

## 2. 目标

| 目标 | 含义 | 反面（不做）|
|---|---|---|
| 感知 | 让架构师在有限认知带宽内维持正确的系统心智模型 | 把全部信息摆出来让人自己过滤 |
| 对抗认知卸载 | AI 可以生成描述、建议分类、起草规则，但没有被人确认的东西只是主张；代码一变，确认失效 | 架构师对 AI 的输出一键盖章 |
| 演化治理 | 以当前结构起草目标态，实现中与实现后按草图与规则验收，决策留痕 | 只画现状图；只写规范不验收 |

## 3. 系统认知

- **系统 = 结构 + 行为 + 原则。** 结构是模块、关系、契约；行为是场景穿过结构的路径；原则是为什么这样分（层的抽象、封闭、允许依赖）。三者必须相互一致，任一缺失都不是完整的架构描述。
- **关系表达交互，不表达知识。** 关系只有四类交互：查询（`queries`，要结果、无副作用，后果归调用方，同步缺省、可异步）、委托（`commands`，控制权交出，被调方拥有后果，同步或异步）、通知（`notifies`，委托的一对多，发布者不知道订阅者，一律异步）、流（`streams`，连续数据，关注吞吐与背压）。**机制是修饰不是类型**：经什么连（直接 / 端口 / 总线 / 通道，`via`）、异步、拉取。读一条线用**三问四修饰**：①被调方拥有后果吗——否即查询；②是，发起方知道接收方吗——知道即委托，不知道、一对多即通知；③传的是连续数据吗——是即流；④再读修饰。「谁导入谁」「谁实现了哪个端口」「谁继承谁」「谁组装谁」都是代码事实，由工具从源码算出，不由人或 AI 写成关系；端口是一等实体，带实现者事实。分类是 AI 的主张，架构师只确认核心模块之间的线（[ADR-0026](../adr/0026-relations-are-interactions.md)、[ADR-0029](../adr/0029-interaction-kinds-and-via.md)、[ADR-0030](../adr/0030-boundaries-and-assembly.md)；第六轮已实现）。
- **三张图，一套层次**（[ADR-0031](../adr/0031-three-views-and-structure-view.md)，草案，待负责人裁决）。同一套模块层次上有三种边：**结构图**是依赖事实（谁导入谁、谁组装谁、谁继承谁、谁实现端口），工具从代码算出，回答改哪、牵动哪里、耦合最重在哪、哪些稳定、分层是否被穿透；**交互图**是四类交互的主张，回答做什么、谁负责后果、哪里可替换；**运行图**是场景的有序消息，回答这一次怎么走。三者是包含链——**场景步 ⊂ 交互 ⊂ 依赖**：绑定了关系的一步是一条交互的一次发生，一条直接交互背后是一条依赖；往上加语义，往下做证据：依赖证实交互（K5、K5c），交互证实场景（S19）；有交互使用而没有交互的依赖是未解释的交互（K7），有交互而没有依赖的是未证实（K6），有消息而没有交互的是未建模（P11）；经总线、通道的交互越过导入图，标「不判定」。三张图在同一画布上以视角切换（结构 ｜ 交互 ｜ 运行），节点位置不动。本节首条「系统 = 结构 + 行为 + 原则」里的「结构」含结构图与交互图两层。
- **四个载体。** 意图 = 草图（人拥有）；理解 = 确认层（人确认过的描述）；证据 = 代码事实（工具算出）；自由 = 草图没画的地方（AI 的空间）。来源不限，但必须可区分（ADR-0019、ADR-0023）。
- **草图是思考的介质，模型是记录的载体。** 草图挂在一个模块下、只画一个层次、七个左右节点、自由布局；拆合是设计动作并记血缘；对比只有「相对基线」与「相对当前版本」（ADR-0025）。

## 4. 原则

| # | 原则 | 落点 |
|---|---|---|
| SP1 | 心智模型优先：每个功能要么帮架构师建立或纠正心智模型，要么帮他做一个结构决策，否则不做 | 需求评审的第一问（[01 §4](../01-requirements.md#4-功能需求)） |
| SP2 | 人拥有意图，AI 拥有描述，代码是裁判：三者分开存放、可区分、互相核验 | B 系列规则、X 系列规则、K 系列规则 |
| SP3 | 没有被人确认过的描述只是 AI 的主张：确认层记录人看过并认可的内容，代码变化使确认失效 | Z 系列规则（Z1–Z6）、需复核（Z3） |
| SP4 | 有限带宽：任何视图在任何层次默认不超过七个左右的主体，超出折叠而不缩小；核心、普通、共用件分级（ADR-0027） | O 系列规则（任意层次的分级与折叠 O8–O11）、P18、X13 |
| SP5 | 事实不可隐藏：折叠可以、隐藏不行；每条主张都要能追到代码，追不到的标出来 | K5、K6、S16、S17（步骤的代码证据）；折叠必有计数（O11） |
| SP6 | 事实求全、描述求准、呈现求少：完整性只对代码事实要求；描述只写有架构含义的东西；呈现按带宽取舍 | lint 的方向（Q12）、K7 的定义（未解释的交互） |
| SP7 | 局部可改、整体可验：架构师在局部起草，工具对整体核验（层依赖、环、矛盾、偏差） | 核验与治理：X4、X14、U 系列、Y 系列 |
| SP8 | 决策留痕：每个重要决定记 ADR，草图与各轮是设计的证据，归档后原样可开 | [adr/](../adr/README.md)、设计版本与 ADR 的链接（E7）、草图 `layout`（X15） |
| SP9 | 工具治理自身：架构台用自己描述自己、按自己的流程演化，先在自身验证再推广 | 迭代策略（ADR-0023「推进策略」、CLAUDE.md §3） |

## 5. 已知缺口（按本文原则应补、尚未做）

- 行为没有目标态：草图只画结构，场景没有草图，行为只有现状没有验收（第六轮登记为本轮不做）。
- 决策不是模型里的一等对象：ADR 与模块、草图之间没有链接。第一步：模块的 `adrs` 字段与面板「相关决策」（E9，已实现）。
- depends 仍是关系、第二级以下无分级：分别由 [ADR-0026](../adr/0026-relations-are-interactions.md)、[ADR-0027](../adr/0027-module-roles.md) 解决（均已实现）。
- 数据归属关系：哪个模块拥有哪份状态（单一写者）没有表达；第六轮登记，本轮不做。
- 依赖事实没有自己的投影：静态只以交互图的线型、面板「知识」行、叠加点线、环与违规、端口面板零散出现，「改一处牵动哪里、耦合最重在哪、哪些模块最稳定」没有图答；由 [ADR-0031](../adr/0031-three-views-and-structure-view.md)（草案，待负责人裁决）新增结构视角解决，其中不稳定度 I 由 K16 算出，抽象度 A 与主序列距离仍不做。
- 稳定性 / 抽象度派生指标（如 Martin 的不稳定度 I、抽象度 A 与主序列距离）没有从事实算出；第六轮登记，本轮不做。
- 一条线读不出后果归谁、能不能换（`calls` 混了查询与委托，`implements` 把机制当语义）；边界与组装看不见：由 [ADR-0029](../adr/0029-interaction-kinds-and-via.md)、[ADR-0030](../adr/0030-boundaries-and-assembly.md) 解决（均已实现，第六轮）。
- 组装与「创建并使用」分不清：组装事实（K13）只看 `new` / 工厂 / 注册的出现，不追踪 new 出的实例之后是否被调用，所以「创建后又调用其实例」的交互只能靠描述保留为委托 / 查询（h5player 26 条）；后续可从代码事实追踪实例的调用，把两者分开（第六轮 T4 裁决 1 登记）。
