# 文档地图

文档描述**最终态**，是需求、概念、规则与架构的真源；每类信息只在一个地方写，其他地方按编号或链接引用（[ADR-0004](./adr/0004-docs-structure.md)）。

## 1. 文档与它回答的问题

| 文档 | 回答 | 读者 |
|---|---|---|
| [system/](./system/README.md) | 产品是什么、为谁、按什么原则取舍：定位、目标、系统认知、原则 S1–S9、已知缺口；最高层真源（[ADR-0028](./adr/0028-positioning-and-principles.md)） | 所有人 |
| [01-requirements.md](./01-requirements.md) | 做什么、为什么、做到什么程度：背景、目标、功能需求（带编号、优先级、状态）、非功能、验收标准、后续方向、已决问题 | 所有人 |
| [02-domain.md](./02-domain.md) | 概念是什么、规则是什么：概念定义，领域规则清单（编号、来源、所在模块、状态） | 设计、开发、测试 |
| [03-architecture.md](./03-architecture.md) | 系统怎么组成：设计原则、分层、模块、依赖、技术栈、开发与物理视图、价值链 | 设计、开发 |
| [architecture/](./architecture/) | 每块怎么工作：机制、数据结构、接口、运行时序（8 个专题，索引见总览 §7） | 开发 |
| [04-description-format.md](./04-description-format.md) | 描述文件怎么组织、怎么写；设计版本怎么起草 | AI、描述维护者 |
| [adr/](./adr/README.md) | 为什么这样决定：背景、选项、结论、后果 | 所有人 |

建议阅读顺序：定位与原则 → 需求 → 领域模型 → 架构总览 → 按需读专题；写描述时读描述格式。

## 2. 信息归属（单一真源）

| 信息 | 唯一归属 | 其他文档怎么用 |

| 写法约定、骨架、设计版本流程、架构规则的写法 | 04 | — |
| 基线与拦截记录 | `model/<项目>/governance/`（由命令行与 agent 接口写，不属于描述） | 面板与报告只读 |

## 3. 约定

- **状态标注**：已实现 / 待实现（已定稿未开发）/ 待重构或待迁移（行为已有、实现位置要调整）/ 后续（不在当前范围）。功能实现后改状态，不留「一期 / 二期」式的增量章节。
- **编号**：需求（H、DV、W、C、D、SR、MT、GV、AG、RV、HS、SK）与规则（M、L、O、E、V、N、S、A、F、P、R、T、G、K、U、Y、Q、B、Z、J、X）编号不复用；删除或合并的保留空号并注明去向。
- **一致性检查**：改动任何一份文档时，按 §2 检查引用它的地方：规则改了 → 01 的规则列、专题、单测；描述格式改了 → `schema/`、04、02 §1 的字段含义；模块改了 → 03 模块表、专题、`model/h5p-arch-desk/` 描述；需求改了 → 验收标准。
- **语言**：结论先行、短句、结构化（表格优先）；不写过程叙述（过程在 ADR 与设计版本里）。
