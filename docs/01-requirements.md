# h5p-arch-desk 原始需求文档

> 状态：v1.0 定档（2026-10-19）
> 位置：`h5player-demo/packages/h5p-arch-desk`（与 `auto_test` 同级）
> 服务对象：h5player 架构师与核心工程师

---

## 1. 背景

h5player 的架构信息目前分散在几处：

| 来源 | 内容 | 问题 |
|---|---|---|
| `h5player/docs/arch/blueprint.md` | 四层分层、依赖矩阵、数据面/控制面运行流（mermaid） | 静态图，不能下钻，不能点开看某个模块的接口 |
| `h5player/docs/system/module-map.md` / `.yaml` | 13 个业务板块、模块 ID（`M-ARC-1` 等）与源码 glob | 面向覆盖率统计，只有归属，没有模块间关系 |
| `h5player/docs/design/0-kernel … 9-foundation` | 各模块设计文档 | 按文档组织，看不到全局 |
| `h5player/.dependency-cruiser.cjs` | 包级依赖门禁 | 只管 4 个包，粒度太粗 |

架构师要回答「这个模块负责什么、对外暴露什么、和谁通过什么接口交换什么数据、一次播放请求依次经过哪些模块」时，需要在多份文档和代码之间来回翻。h5p-arch-desk 要把这些信息收拢成**一张可以下钻、可以点选查看属性的模块关系图**。

## 2. 目标与非目标

### 2.1 目标

1. **看见结构**：以模块为基本单元，分层次呈现 h5player 的模块与模块间关系。
2. **看见运行**（二期）：在静态结构上叠加时序，呈现一次业务流程依次、分支、循环、异步地调用了哪些模块。
3. **看见演化**（后续）：架构描述随代码一起进 git，可以对比两个版本之间模块和关系的增删改。
4. **支撑治理**（后续）：架构描述与真实代码依赖做比对，发现偏航。

### 2.2 非目标

- 不展示文件、函数、类等模块以下的代码细节。模块以下交给 AI 和工程师实现。
- 一期不做画布内的图形化编辑（拖线建关系、表单改属性）。架构描述以文本文件维护，可由人或 AI 修改。
- 不替代设计文档。属性面板可以链接到 `docs/design/**` 的对应文档，但不搬运全文。

## 3. 核心概念

> 原则：**架构 = 模块 + 模块间关系，按层次抽象。** 价值在「模块各司其职 + 通过接口交换信息和控制权」的执行链路上产生。

### 3.1 模块（Module）

系统中承担一组明确职责的单元。模块可以包含子模块，形成树。

| 属性 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 全局唯一、稳定，如 `kernel.state-machine`；建议能映射到 module-map 的 `M-xxx` |
| `name` | ✅ | 显示名，如「状态机」 |
| `kind` | | 模块类别，如 `layer` / `package` / `subsystem` / `component`，用于配色和图标 |
| `responsibility` | ✅ | 职责：一两句话说清它负责什么、不负责什么 |
| `principle` | | 实现原理：核心机制的文字说明（Markdown） |
| `dataStructures` | | 核心数据结构，引用 §3.4 的数据结构定义 |
| `provides` | | 对外提供的接口，引用 §3.3 的接口定义 |
| `children` | | 子模块列表 |
| `codeRefs` | | 对应的源码 glob 或 module-map ID（用于后续治理比对，面板只显示不展开） |
| `docRefs` | | 相关设计文档链接 |
| `status` | | `current`（已落地）/ `target`（蓝图目标态）/ `deprecated` |
| `core` | | 是否核心模块；为 `true` 时会在上一级的分层总览中直接露出（见 §3.6） |
| `owner` / `tags` | | 负责人、标签 |

`kind: layer` 的模块（层）额外有以下字段：

| 属性 | 必填 | 说明 |
|---|---|---|
| `order` | ✅ | 层序，数字越小越靠上（越靠近外部、越易变） |
| `abstraction` | ✅ | 抽象原则：一句话说明这一层按什么标准划分，如「规则与事实；纯决策，无 DOM / 网络」 |
| `includes` / `excludes` | | 应该包含 / 不应该包含什么（对应 blueprint §2.3 的表） |
| `mayDependOn` | | 允许依赖的层 ID 列表（对应 blueprint §2.2 依赖矩阵）；只用于展示，一期不做校验 |

### 3.2 关系（Relation）

两个模块之间的一条有向联系。

| 属性 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 全局唯一 |
| `from` / `to` | ✅ | 两端模块 ID，可以是任意层级的模块 |
| `type` | ✅ | 关系类型，见下表 |
| `interface` | | 经由的接口，引用 §3.3 |
| `payload` | | 交换的数据结构，引用 §3.4 |
| `mode` | | `sync` / `async` |
| `description` | | 说明（Markdown） |

关系类型（一期固定枚举，后续可扩展）：

| type | 含义 | 例子 |
|---|---|---|
| `depends` | 编译期依赖（import） | domain → share |
| `calls` | 运行时调用，控制权转移 | Solution → Pipeline.updatePipeline |
| `dataflow` | 数据推送，数据面 | Demuxer → DemuxedBuffer |
| `event` | 事件发布/订阅 | StateMachine → 插件 |
| `implements` | 实现某个端口/契约 | MU 实现 Domain.Ports |

约束：
- 祖先与后代之间不允许建关系（包含关系由树结构表达）。
- 同一对模块之间可以有多条不同类型或不同接口的关系。

### 3.3 接口（Interface）

模块对外暴露的能力。独立定义、可被多个模块和关系引用：`id`、`name`、`owner`（提供方模块）、`signature`（TS 风格签名文本）、`description`、`semantics`（前置条件、副作用、错误）。

### 3.4 数据结构（DataStructure）

接口和关系中交换的数据定义：`id`、`name`、`definition`（TS 类型文本）、`description`、`invariants`（不变量）。

### 3.5 视图层次（Level）

「当前层次」= 某个父模块（根层次的父模块是系统本身）。画布只呈现**该父模块的直接子模块**和**它们之间的关系**，更深和更外的信息默认屏蔽。

关系在层次间的投影规则（本工具最关键的规则）：

1. 关系两端都是当前层次可见模块 → 直接画。
2. 两端落在当前层次两个不同子模块的**内部**（后代）→ 提升为这两个子模块之间的一条**聚合边**，边上标注条数；选中聚合边时，面板列出被聚合的原始关系。
3. 两端都在同一个子模块内部 → 当前层次不画（属于更深层次的事）。
4. 一端在当前父模块**外部** → 外部端点以淡色「边界节点」呈现（显示其名称和所在路径），统一排在内部结构下方一行，可通过开关隐藏。指向边界节点的边**默认不画**，只在悬停或选中相关模块（或该边界节点）时出现，避免外部关系淹没本层结构。
5. 普通层次中，同一对模块之间的关系不论类型合并成一条边：颜色取条数最多的类型，标注条数，面板中列出各类型条数与原始关系。分层总览仍按类型分开（边少，类型差异是关键信息）。

### 3.6 分层总览（全局视角）

当某个父模块的直接子模块都是层（`kind: layer`）时，这一层次不用普通图呈现，而是用**分层总览**呈现。根层次就是这种情况。

目标：一张图看清全貌，包括有几层、每层按什么原则划分、层间怎么依赖、每层有哪些核心模块。

呈现规则：

1. **按层序分带**：每层是一条横向的带，按 `order` 从上到下固定排列，不参与自动布局。
2. **带内三栏**：左栏显示层名和 `abstraction`；中栏显示该层 `core: true` 的子模块，非核心模块折叠成「+N」；右栏显示 `mayDependOn`。
3. **层间依赖**：带与带之间画层级的聚合边并标注条数（规则同 §3.5）。跨越多层的依赖，例如 Infrastructure → Share，画在带的侧边，避免穿过中间的带。
4. **核心模块的关系默认隐藏**：悬停或选中某个核心模块时，才高亮它的跨层关系，避免总览图变成一团线。
5. **这是「每层只看本层」原则的唯一例外**：只多展开一层，而且只展开核心模块。

交互：

- 单击带 → 面板显示该层的抽象原则、包含 / 不包含、可依赖的层、全部子模块列表。
- 双击带 → 下钻进入该层（普通图）。
- 单击核心模块 → 选中它，面板显示模块属性。
- 双击核心模块 → 直接下钻到该模块，面包屑补全中间的层。

这个规则不限于根层次。任何子系统只要它的子模块被标为层，进入它时也按分层总览呈现。

## 4. 一期 MVP 功能需求

### 4.0 项目列表主页

工具可同时承载多个项目的架构描述（如 h5player 与 h5p-arch-desk 自身），每个项目是模型根目录下的一个子目录（见 §4.4）。

| 编号 | 需求 | 优先级 |
|---|---|---|
| H-1 | 首页列出全部项目，每个项目一张卡片：名称、ID、简介、根下的层（或顶层模块）、规模（模块 / 关系 / 接口 / 数据结构数）、生成来源（提交、时间）、错误与提醒数 | P0 |
| H-2 | 点击卡片进入该项目的架构视图（§4.1 起的全部能力）；每个项目的层次与选中互不影响 | P0 |
| H-3 | 项目视图的面包屑以「项目」开头，点击回到首页；在项目根层按 Backspace 也回到首页；浏览器后退可在首页与项目间往返 | P0 |
| H-4 | 项目不存在或描述读取失败时，给出原因并提供「返回项目列表」 | P0 |
| H-5 | 开发态任一项目的描述变化后，首页摘要与该项目视图自动刷新；其他项目不受影响 | P1 |

### 4.1 整体布局

- 左右布局：左侧**画布区**，右侧**属性面板区**；两区之间分隔条可拖动，面板可折叠。
- 顶部：面包屑（当前层次路径，可点击跳回任意上级）、搜索框、视图开关（显示边界节点 / 关系类型筛选）。

### 4.2 画布区

| 编号 | 需求 | 优先级 |
|---|---|---|
| C-1 | 以节点表示模块、有向边表示关系，整体为图结构 | P0 |
| C-2 | 平移（拖拽空白处）、缩放（滚轮 / 触控板捏合）、适应画布（一键 fit） | P0 |
| C-3 | 单击节点 / 边 → 选中，高亮并在面板显示属性；单击空白 → 取消选中，面板显示当前父模块属性 | P0 |
| C-4 | 双击有子模块的节点 → 下钻到该模块的层次；无子模块时双击无效果（节点上有「可下钻」标识） | P0 |
| C-5 | 返回上级：面包屑点击、`Backspace`/`Esc`、浏览器后退 | P0 |

| C-8 | 聚合边、边界节点按 §3.5 规则呈现 | P0 |

| C-8b | 分层总览中悬停或选中核心模块时，高亮它的跨层关系 | P0 |

| C-9 | 悬停节点时高亮其相邻边和节点 | P1 |
| C-10 | 当前层次 + 选中对象写进 URL，复制链接可直接打开同一视图 | P1 |
| C-11 | 搜索模块名 / ID，选中结果后跳到其所在层次并选中 | P1 |
| C-12 | 手动拖动节点调整位置，位置可保存到描述文件 | P2 |
| C-13 | 小地图（minimap） | P2 |

### 4.3 属性面板区

选中对象不同，面板内容不同：

| 选中对象 | 面板内容 |
|---|---|
| 模块 | 名称、ID、类别、状态；职责；实现原理；核心数据结构（展开看定义）；对外接口（展开看签名与语义）；子模块列表（可点击下钻）；入边 / 出边列表（可点击选中）；代码与文档引用 |
| 关系 | 类型、方向（from → to，均可点击）、同步/异步；经由接口的签名与语义；交换的数据结构定义；说明 |
| 聚合边 | 被聚合的原始关系列表，每条可点击跳到其真实所在层次并选中 |
| 无选中 | 当前父模块的属性 |

文本字段支持 Markdown；签名和类型定义以代码块显示并做语法高亮。

### 4.4 数据维护

- 架构描述以 YAML 文本文件存放，结构见技术选型文档 §4。模型根目录（默认 `model/`）下每个含 `system.yaml` 的子目录是一个项目。
- 本地开发时修改描述文件，页面自动刷新且保持当前层次和选中状态。
- 加载时做结构校验：引用不存在的模块/接口/数据结构、ID 重复、祖先-后代关系等错误要在页面上明确报出（文件、位置、原因），不静默忽略。
- 提供命令行校验（`npm run lint:model`），可接入 CI。

### 4.5 初始内容

一期至少录入：
- 根层次：Share / Domain / Application / Infrastructure 四层（来自 `blueprint.md §2.1`）及层间依赖；每层填写 `order`、`abstraction`、`includes` / `excludes`（来自 §1.2、§2.3）和 `mayDependOn`（来自 §2.2），并标出各层的核心模块。
- 第二层：blueprint §2.1 中各子模块（PlayerIndex、Framework mechanisms、MUs、Solution、Fragments、Factories、Registry、Services、Models、Ports、Algorithms）及其关系。
- 至少一条下钻到第三层的完整示例（建议 Framework → StateMachine / Pipeline / Plugin / Event / ModelRegistry），每个模块的职责、接口、数据结构填写完整。

## 5. 二期 MVP：动态视角

### 5.1 概念：场景（Scenario）

一条有名字的执行链路，例如「首次 play」「方案切换事务」「seek」。场景由有序的**步骤**组成：

| 步骤类型 | 含义 |
|---|---|
| `call` | 一次调用 / 消息：from 模块 → to 模块，可引用某条关系或接口，携带数据结构 |
| `return` | 返回（可选，默认由 call 隐含） |
| `alt` | 分支：若干条件分支，每个分支是一组步骤 |
| `loop` | 循环：循环条件 + 一组步骤 |
| `par` | 并行 / 异步：若干同时进行的步骤组 |
| `async` | 异步投递（发出后不等待），如事件发布、postMessage 到 Worker |
| `ref` | 引用另一个场景（复用子流程） |

### 5.2 功能

| 编号 | 需求 | 优先级 |
|---|---|---|
| D-1 | 场景列表：可按层次筛选，选择一个场景进入动态视角 | P0 |
| D-2 | 时序图视图：参与模块为泳道，步骤按时间自上而下，`alt`/`loop`/`par` 以框表示 | P0 |
| D-3 | 图上回放：在结构图上按步骤顺序高亮边和节点，支持单步前进/后退、自动播放、跳到任意步骤 | P0 |
| D-4 | 层次一致：场景步骤的端点按 §3.5 规则投影到当前层次；下钻后同一场景显示更细的步骤（若描述了更细的步骤） | P0 |
| D-5 | 选中某个步骤 → 面板显示该步骤的接口、数据结构、条件说明 | P0 |
| D-6 | 异步步骤与同步步骤视觉上可区分（线型、箭头） | P0 |
| D-7 | 时序图与结构图联动：在任一视图选中步骤，另一视图同步定位 | P1 |
| D-8 | 场景与 blueprint 中现有 mermaid 时序图对照迁移（§4.2 控制面、§4.3 切换事务） | P1 |

## 6. 后续方向（不在两期 MVP 内，但数据模型需预留）

1. **演化**：选两个 git 版本，对比模块/关系/接口的增删改并在图上标色；时间轴回看。
2. **治理比对**：用 `codeRefs` + dependency-cruiser 扫描结果，比对「描述中的依赖」与「代码中的真实依赖」，列出缺失或越界的边。
3. **AI 协作**：在面板上就选中模块向 AI 提问、让 AI 起草模块描述或根据代码补全接口定义。
4. **画布内编辑**：直接在画布上增删模块和关系，写回描述文件。

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 规模 | 单层次 ≤ 50 节点、≤ 150 边时，交互流畅（平移缩放 ≥ 50fps）；全模型 ≤ 1000 模块时首屏加载 < 2s |
| 运行方式 | 本地 `npm run dev` 启动；可 `npm run build` 产出静态站点部署到内网 |
| 浏览器 | 最新版 Chrome / Edge / Safari 桌面端 |
| 只读安全 | 一期页面不写文件；不依赖后端服务 |
| 可测性 | 模型解析、校验、层次投影规则必须有单元测试 |

## 8. 验收标准（一期）

1. 打开首页看到分层总览：4 条带从上到下排列，每条带显示抽象原则、核心模块和可依赖的层，带间有层间依赖及条数；能平移、缩放、fit。不下钻就能说出「有几层、每层管什么、谁依赖谁、每层的核心模块是哪些」。
2. 点击任意模块或边，右侧面板显示 §4.3 规定的内容。
3. 双击 Infrastructure → 看到其子模块；再双击 Framework → 看到第三层；面包屑可逐级返回。
4. 在第二层能看到由更深层关系提升出的聚合边，选中后能列出原始关系并跳转。
5. 故意在 YAML 中引用一个不存在的模块 ID，页面与 `npm run lint:model` 都报出明确错误。
6. 修改 YAML 中某模块的职责文字，页面自动更新，当前层次与选中状态保持不变。
7. 首页列出 h5player 与 h5p-arch-desk 两个项目；点击任一进入其分层总览，面包屑「项目」返回首页，浏览器后退回到上一个项目的原层次。
