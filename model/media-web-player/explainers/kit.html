为什么门面不判断状态

如果门面也看状态（比如「已经在播就不再发 play」），判断就有了两处：门面一次，内核施用时一次。两次之间状态可能已经被排在前面的命令改掉了，于是同一串操作快着点和慢着点会得到不同的结果。 所以门面只做翻译：宿主调一个方法，门面就提交一条命令，把内核给的「受理 / 拒绝原因」原样还给宿主。能不能受理只在一处判：内核按队列轮到这条命令时，去问会话规则。

为什么规则要从内核里抽出来

「在什么状态下接受什么命令」「这个容器该走哪个族、哪条路线」「事件流的顺序对不对」都是表和纯函数，不需要时钟、不需要浏览器，抽出来就能逐条单测，也能被宿主侧的测试复用（顺序机检就是给宿主核对事件流用的）。 内核只调用它们，不内嵌它们，所以改一条规则不会碰到队列与释放这些难测的部分。会话规则自己守住的是：

    为什么页面能力单独成块

    AudioContext 与屏幕常亮是整页一份的东西：页面上可以有几个播放器、一个播放器可以开关很多次会话，它们都共用同一个声音上下文。 如果放进内核，它们的寿命就会被绑到会话上——关一次会话就关一次 AudioContext，下一次播放就得重新要一次用户手势。 所以它们由门面在创建时建好、以接口注入内核；内核只经接口问「声音是不是真在跑」「现在要不要常亮」，不碰浏览器 API。

    管线族为什么由宿主注入

    Kit 不认识任何具体的管线族：它只认管线契约里的族端口。宿主决定装哪些族（元素族、自时钟族……），门面逐族建立、交给内核；内核打开会话时按会话规则选出的路线，把会话交给对应族的管线。 这样 Kit 可以先发版，新的族不需要改 Kit；门面这一侧守住的是：

      常见误解

      误解实际
      「play() 返回成功就说明在播了」返回的是这条命令是否被受理；真正开播看 state 事件（首帧后才从 loading 变为 playing）。
      「规则在门面里，所以门面能挡掉非法调用」门面不挡；受理与否只由内核在轮到这条命令时查会话规则决定。
      「关掉会话会关掉声音上下文」不会；页面能力比会话活得久，会话只释放它自己获取的资源。
